# 共通ルールの仕様

## 概要

`spec/001_boards.md` / `spec/002_lists.md` / `spec/003_cards.md` が共通で参照するルールをまとめる。
本ファイルに書かれた規定は各機能仕様書に再掲せず、参照のみを行う。
`constitution.md` に定義された技術スタック、非機能要件、権限ポリシー、用語集を前提とする。

## HTTP ステータスコードとエラーレスポンス

`constitution.md § コーディング規約` に従い、以下の 5 種類を用途に応じて返す。エラー時の JSON は
`{ "error": { "code": "<エラーコード>", "message": "<日本語メッセージ>" } }` に統一する。

| ステータス | エラーコード | 用途 |
|---|---|---|
| `422 Unprocessable Entity` | `VALIDATION_ERROR` | 入力バリデーション失敗（フィールド別詳細は `details` に格納する場合あり） |
| `401 Unauthorized` | `UNAUTHORIZED` | 未認証（未ログイン） |
| `403 Forbidden` | `FORBIDDEN` | 権限不足（認証済みだが操作権限なし） |
| `404 Not Found` | `NOT_FOUND` | 対象リソースが存在しない、または閲覧権限がない |
| `500 Internal Server Error` | `INTERNAL_ERROR` | 予期しないサーバー側エラー |

`VALIDATION_ERROR` の場合、フィールド別違反を含める場合は
`{ "error": { "code": "VALIDATION_ERROR", "message": "...", "details": { "<field>": "<理由コード>" } } }` の形にする。

## Route Handler の入口チェック順序

`constitution.md § 権限チェックの実装方針` に従い、Route Handler の入口で以下の順で判定する。
順序を守ることで、認証エラーと権限エラーと未存在エラーが混在しない。

1. 認証チェック → 未ログインなら `401 UNAUTHORIZED`
2. 対象リソース存在チェック → 存在しない・閲覧不可なら `404 NOT_FOUND`（存在の有無を漏らさない）
3. 権限チェック → 権限不足なら `403 FORBIDDEN`
4. 入力バリデーション → 失敗なら `422 VALIDATION_ERROR`
5. 業務処理 → 成功なら `2xx`

## 権限マトリクス（本 spec 対象操作）

`constitution.md § 権限ポリシー` に基づき、本 spec が扱う操作の必要権限を整理する。

| 操作カテゴリ | owner | member | viewer |
|---|---|---|---|
| ボード作成 | 可 | 不可 | 不可 |
| ボード編集 (`title`) | 可 | 不可 | 不可 |
| ボード削除 | 可 | 不可 | 不可 |
| リスト作成、編集、削除、並び替え | 可 | 可 | 不可 |
| カード作成、編集、削除、並び替え | 可 | 可 | 不可 |
| ボード、リスト、カードの閲覧 | 可 | 可 | 可 |

権限のないユーザーが操作を試みた場合、`§ Route Handler の入口チェック順序` に従い `403` を返す。
対象リソースの閲覧権限が無い場合は `404` を返し、存在有無を露出させない。

## リソース識別子

- 全てのリソース ID は文字列型で扱う。
- ID の生成方式（cuid / uuid など）は設計工程（`design/`）で決定する。本 spec では ID の存在と一意性のみを前提とする。

## 並び順 (`order`)

- Board、List、Card は同一スコープ内での並び順を `order` フィールドで保持する。
  - Board の並び順スコープ = ユーザーごとの全体
  - List の並び順スコープ = 同一 `boardId` 内
  - Card の並び順スコープ = 同一 `listId` 内
- 新規作成時のデフォルト位置は、同一スコープの末尾（既存の最大 `order` + 1、0 件なら 0）。
- 並び替え API は「対象リソースを、指定した位置に移動する」操作として提供する（本章 02 セクションでは並び替え API は範囲外、末尾追加のみ）。
- `order` の内部表現（整数連番 / 小数点差分 / 隣接キー）は設計工程で決定する。本 spec では「同一スコープ内で一意な順序が保存され、取得時に昇順で並ぶ」ことのみを要求する。

## タイムスタンプ

- `createdAt` はレコード作成時に自動設定する。
- `updatedAt` はレコード作成時と更新時に自動設定する。
- 並び替えのみを行う操作でも `updatedAt` を更新する。
- 表現形式は ISO 8601 の UTC を前提とする（例: `2026-07-18T09:00:00.000Z`）。

## カスケード削除

- ボード削除時、そのボードに属する全てのリストと全てのカードを削除する。
- リスト削除時、そのリストに属する全てのカードを削除する。
- カスケード削除の実装方式（DB 制約 / アプリ層）は設計工程で決定する。

## 一覧 API のレスポンス構造

- 一覧 API は配列を直接返さず、オブジェクト `{ "items": [...] }` を返す。
- 0 件の場合も `200` で `{ "items": [] }` を返す。
- 一覧はページネーションを行わず、全件を返す（本章 02 セクションの初期実装範囲）。
- 一覧の並び順は `order` 昇順を第一キー、`createdAt` 昇順を第二キーとする。

## 空状態の扱い

- ボード一覧画面、ボード詳細画面、リスト、カードのいずれも 0 件時に「空状態」を表示する。
- 空状態は「該当データが 0 件である」ことと「新規作成の導線」を示す。
- 具体的な文言と装飾は UI 設計工程（`ui-design/`）で決定する。

## 認証の前提

- 本 spec は「認証機構が既に存在し、Route Handler で現在ユーザーを取得できる」ことを前提とする。
- 認証機構そのもの（ログイン画面、セッション管理、ユーザー登録、招待）は本 spec の対象外で、`§ 未決事項` に列挙する。
- 初期実装では、開発用の固定ユーザー（`dev-user`）を「ログイン中のユーザー」として扱ってよい。切替方式は設計工程で決定する。

## 監査ログ

- 全ての作成、更新、削除、並び替え操作について、操作ログを追跡可能な形で残す（対象リソース種別・ID、操作種別、実行ユーザー、時刻、リクエスト ID）。
- ログの保存先と実装方式は設計工程で決定する。

## 非機能要件

`constitution.md § 非機能要件` に従う。本 spec の各機能に対する具体化は以下の通り。

- 性能: 一覧 API（Board / List / Card 取得）は P95 200ms 以内、作成、更新、削除 API は P95 300ms 以内。
- 運用: エラーレスポンスを返した場合、そのステータス、エラーコード、対象リソース識別子、操作ユーザー識別子、リクエスト ID をログに記録する。
- セキュリティ: `constitution.md § セキュリティ` に従い、本 spec は SQLite ローカル環境を前提とする。
