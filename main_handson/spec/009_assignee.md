# 担当者（Assignee）の仕様

## 概要

カードに担当者（ユーザー）を割り当てる機能。カードへの担当者の追加・削除・一覧取得と、カード詳細での担当者表示を定義する。1カードの担当者は最大10名。

本仕様は担当者機能全体の完成イメージを記述する。本章の TDD では、このうち外部依存を持たない純粋関数の受入条件（担当者入力のバリデーションと人数上限判定）だけを実装・テストする（§ TDD スコープ 参照）。

## 既存仕様との関係

- 共通規約は `spec/000_shared_rules.md` を参照する。
- 担当者はカード（`spec/003_cards.md`）に紐づく。カード詳細での表示は `spec/005_card_detail.md`（担当者領域を追加）。
- 担当者はボード（`spec/001_boards.md`）のメンバーである User を対象とする。User / ボードメンバー（BoardMembership）は認証・招待・権限機能（後続）で確定するモデルを前提とし、本仕様では「ボードメンバーであること」を担当者化の条件として参照する。

## 対象データ

- CardAssignee（カードと担当者ユーザーの中間テーブル）
  - `id`: string（サーバー採番）
  - `cardId`: string（対象カード）
  - `userId`: string（担当者ユーザー）
  - `createdAt`: datetime
  - 同一 `(cardId, userId)` の重複は作らない（ユニーク）。
- 1カードあたりの CardAssignee は最大10件。
- User / BoardMembership は後続機能で確定（本仕様ではメンバー判定の入力として参照）。

## 機能要件

### 操作: 担当者の追加（FR-001）

- 対象カードに `userId` の担当者を追加する（CardAssignee を作成）。
- 追加できるのは、対象ユーザーが対象カードの属するボードのメンバーである場合のみ。
- 完了条件: 追加後、担当者一覧に当該 `userId` が含まれ、件数が +1 される。

### 操作: 担当者の削除（FR-002）

- 対象カードから `userId` の担当者を削除する（CardAssignee を削除）。
- 完了条件: 削除後、担当者一覧に当該 `userId` が含まれず、件数が −1 される。

### 操作: 担当者一覧の取得（FR-003）

- 対象カードの担当者一覧を取得する。
- 完了条件: `{ items: [...] }` 形状で、割り当て済みの担当者を返す。

### 操作: 担当者入力のバリデーション（FR-004、純粋関数）

- `userId` が空でない文字列であることを検証する。
- 完了条件: 空文字・非文字列は不正、1文字以上の文字列は妥当と判定する。

### 操作: 担当者数の上限判定（FR-005、純粋関数）

- 現在の担当者数をもとに、追加可否を判定する。
- 完了条件: 現在9人なら追加を許可し、10人なら追加を拒否する（上限10）。

## 画面

- カード詳細モーダル（`spec/005_card_detail.md`）に担当者領域を追加する。
  - 割り当て済み担当者をアバター/名前で表示する。
  - 担当者の追加（ボードメンバーから選択）・削除ができる（member 以上）。
  - 担当者が 0 人のときは「担当者なし」を表示する。
  - 担当者が上限（10名）のとき、追加操作を無効化または拒否表示する。
- 画面状態: 担当者選択パネル 閉 ⇄ 開、追加/削除の即時反映。
- （注: 担当者 UI の実装は後続工程。本章の TDD 対象外。）

## API

| メソッド | パス | 用途 | 必要権限 |
|---|---|---|---|
| GET | /api/cards/[cardId]/assignees | 担当者一覧取得 | viewer 以上 |
| POST | /api/cards/[cardId]/assignees | 担当者の追加（body: `{ userId }`） | member 以上 |
| DELETE | /api/cards/[cardId]/assignees/[userId] | 担当者の削除 | member 以上 |

## 受入条件

純粋関数（本章 TDD 対象）:

- [ ] `userId` が空文字のとき、担当者入力バリデーションは不正（false / エラー）を返す（FR-004）
- [ ] `userId` が非文字列（number / null / undefined 等）のとき、バリデーションは不正を返す（FR-004）
- [ ] `userId` が1文字以上の文字列のとき、バリデーションは妥当（true）を返す（FR-004）
- [ ] 現在の担当者数が 9 のとき、上限判定は追加を許可する（FR-005）
- [ ] 現在の担当者数が 10 のとき、上限判定は追加を拒否する（FR-005）
- [ ] 現在の担当者数が 0 のとき、上限判定は追加を許可する（FR-005、境界下限）

統合（実 DB・認証モックを用意する後続実装の範囲。純粋関数の PASS だけでは実装済みとしない）:

- [ ] POST /api/cards/[cardId]/assignees に有効な `userId` を渡すと 201（または 200）で担当者が追加される（FR-001）
- [ ] 同じ `userId` を2回追加すると 409 を返す（重複）（FR-001）
- [ ] ボードメンバーでない `userId` を追加すると 422 / VALIDATION_ERROR を返す（FR-001）
- [ ] 担当者が10名のカードに11人目を追加すると 422 / VALIDATION_ERROR を返す（FR-001、上限超過）
- [ ] 存在しない `cardId` への追加・削除・一覧は 404 / NOT_FOUND を返す（FR-001/002/003）
- [ ] 存在しない `userId` の追加は 404 / NOT_FOUND を返す（FR-001）
- [ ] GET /api/cards/[cardId]/assignees は `{ items: [...] }` 形状で 200 を返す（FR-003）
- [ ] 担当者が 0 人のとき GET は `{ items: [] }` を 200 で返す（FR-003）
- [ ] DELETE /api/cards/[cardId]/assignees/[userId] は 200 を返し、担当者が外れる（FR-002）
- [ ] 未認証で追加・削除を行うと 401 / UNAUTHORIZED を返す
- [ ] member 権限のないユーザーが追加・削除を行うと 403 / FORBIDDEN を返す（閲覧権限もない場合は 404）

## 異常系

- 存在しない `cardId` / `userId` は 404 / NOT_FOUND。
- `userId` が空文字・非文字列は 422 / VALIDATION_ERROR。
- ボードメンバーでない `userId` は 422 / VALIDATION_ERROR。
- 同一ユーザーの重複追加は 409。
- 担当者数が上限（10名）を超える追加は 422 / VALIDATION_ERROR。
- 未認証は 401 / UNAUTHORIZED。member 権限なしは 403 / FORBIDDEN（閲覧権限もない場合は 404）。

## 境界条件

- 担当者 0 人: 一覧は空配列。追加は許可。
- 担当者 9 人: 追加を許可（追加後10人）。
- 担当者 10 人: それ以上の追加を拒否（11人目は 422）。
- 存在しないカード: 404。
- 存在しないユーザー: 404。
- `userId` 空文字: 不正（純粋関数 false、API 422）。

## バリデーション

- `cardId`: 必須（パス）。存在しなければ 404。
- `userId`: 必須。空でない文字列であること。空文字・非文字列は不正（純粋関数 false / API 422）。存在しないユーザーは 404。ボードメンバーでなければ 422。
- 担当者数: 追加時、現在の担当者数が 10 未満であること。10 以上は拒否（API 422）。

## 権限境界

| 操作 | 必要権限 | 異常時の動作 |
|---|---|---|
| 担当者一覧取得 | viewer 以上 | 権限なしは 404、未認証は 401 |
| 担当者の追加 | member 以上 | 権限不足は 403、未認証は 401、存在なしは 404、非メンバー/上限/空 userId は 422、重複は 409 |
| 担当者の削除 | member 以上 | 権限不足は 403、未認証は 401、存在なしは 404 |

## カード詳細画面での表示

- カード詳細モーダルの担当者領域に、割り当て済み担当者を表示する（アバター/名前）。
- 0 人のときは「担当者なし」。
- member 以上は追加/削除でき、上限（10名）到達時は追加操作を抑止する。

## 非機能要件

- 担当者一覧取得の応答時間は200ms以内、追加・削除の応答時間は300ms以内（constitution.md § 性能）。
- 担当者の追加・削除は操作ログにリクエスト ID 付きで記録する（spec/000_shared_rules.md）。

## 使用する用語

- 担当者（Assignee）／カード（Card）／ボード（Board）（constitution.md § 用語集 参照）

## TDD スコープ（本章）

本章（セクション06〜08）では、外部依存を持たない次の純粋関数の受入条件のみを実装・テスト・レビューする。

- FR-004: `userId` が空でない文字列であることの検証（`lib/schemas/assignees.ts` 想定）。
- FR-005: 現在の担当者数による追加可否判定（9→許可 / 10→拒否、上限10）（`lib/assignees/limit.ts` 想定）。

API の 409 / 422 / 401 / 403、カード・ユーザーの存在確認、ボードメンバー判定、DB 更新、カード詳細 UI は、実 DB と認証モックを用意する統合実装の範囲であり、本純粋関数の PASS だけでは実装済みとしない。
