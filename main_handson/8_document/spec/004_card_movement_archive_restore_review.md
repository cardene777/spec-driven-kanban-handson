## 観点1: 曖昧表現

### 曖昧-1 [High] FR-002-1 「元位置を試みる」 の挙動が定義されていない

- 問題箇所
  - line 104
  - 「初期方針: 詰めない、`order` は保持しておき復元時に元位置を試みる」
- 問題の理由
  - 「元位置を試みる」 が具体的な挙動として定義されていない。
  - 元位置が既に別カードで占有されている場合、元位置に既存カードが挿入されているだけの場合、元 `order` を上書きする場合、末尾に落とす場合、いずれも成立し得る。
  - FR-002-2 (line 110) では「復元先リストの末尾に配置する」 と別の方針が書かれており、FR-002-1 と FR-002-2 で意図が食い違う (矛盾-1 参照)。
- 修正案 (2 択)
  - 案 A: FR-002-1 の「`order` は保持しておき復元時に元位置を試みる」 部分を削除し、「復元時の配置は FR-002-2 に従い末尾に配置する」 に統一する。
  - 案 B: FR-002-2 を「元位置に空きがあれば元位置、無ければ末尾」 に書き換え、FR-002-1 の記述と合わせる。
- 確認が必要な判断点
  - 復元時のカード配置ルールを「常に末尾」 とするか「元位置優先」 とするか。ハンズオンとしては「末尾」 で統一する方が実装が単純で ACも書きやすい。

## 観点2: 抜け漏れ

### 抜漏-1 [High] archived / deleted 状態カードに対する既存 API `GET /api/cards/{cardId}` / `PATCH /api/cards/{cardId}` の挙動未定義

- 問題箇所
  - `§ API` (line 148-164) と `§ 対象データ § Card エンティティへの追加フィールド` (line 30-42)
- 問題の理由
  - spec/003 § API では `GET /api/cards/{cardId}` (viewer 以上) と `PATCH /api/cards/{cardId}` (member 以上、`title` / `description` を更新) を定義している。
  - spec/004 では「既定の一覧 API (`GET /api/lists/{listId}/cards`) から除外」 は明示 (line 38-40 / 102) しているが、単発取得 `GET /api/cards/{cardId}` と編集 `PATCH /api/cards/{cardId}` が archived / deleted 状態のカードに対してどう振る舞うかが未定義。
  - 想定される 4 通り
    - (a) archived / deleted カードも `GET /api/cards/{cardId}` で取得可能 (状態フィールド付き)
    - (b) archived カードは取得可能、deleted カードは 404
    - (c) 両者とも 404
    - (d) 両者とも取得可能だが `PATCH` は 422 で拒否
  - アーカイブ一覧画面 / 削除済み一覧画面からカード詳細モーダルを開く UX (line 143-144) を想定するなら (a) または (d) が必要。ハンズオン教材として明示すべき。
- 修正案
  - `§ API` の表下に注記を追加。
    - `GET /api/cards/{cardId}` は `status` を問わず対象カードを返す (viewer 以上)。
    - `PATCH /api/cards/{cardId}` は `status = active` のカードのみ受け付ける。`archived` / `deleted` に対しては `422` (`not_editable`) を返す。
  - `§ バリデーションエラー / 状態遷移エラー` 表に「`PATCH /api/cards/{cardId}` を `status ≠ active` のカードに対して呼ぶ → `422` / `not_editable`」 を追加。
  - AC に「アーカイブ一覧画面のカード行から詳細を開くと、`title` と `description` と `archivedAt` が表示される」 を追加。
- 確認が必要な判断点
  - archived / deleted カードの編集を許すか (許すなら FR-002 / FR-003 の状態が編集後にどう変わるかも定義が要る)。教材としては「編集不可 = 422」 で単純化するのが妥当。

### 抜漏-2 [High] リスト削除 / ボード削除時の archived / deleted カードのカスケード削除挙動未定義

- 問題箇所
  - `spec/000_shared_rules.md § カスケード削除` (「ボード削除時、そのボードに属する全てのリストと全てのカードを削除する」 「リスト削除時、そのリストに属する全てのカードを削除する」)
  - spec/004 でカード状態に `archived` / `deleted` が加わったが、カスケード削除対象に含めるかどうかが未定義。
- 問題の理由
  - 復元操作は「元リスト (`listId`) に戻す」 (line 56) が前提で、`restore_target_missing` (line 228) を返す設計。つまり削除されたリスト配下の archived / deleted カードは残り得る (孤児カード)、と読める。
  - 一方でカスケード削除の常識としては、リスト削除で紐づく全カードを消してしまうのが自然。両解釈が可能な状態は実装分岐を招く。
- 修正案 (2 択)
  - 案 A: リスト削除 / ボード削除は archived / deleted 状態のカードも含めて物理削除する。line 56 の記述は「削除されたリストの復元は不可能。削除リストに元々属していた archived / deleted カードは存在しない」 に修正する。復元先が存在しないケース (line 228 `restore_target_missing`) は「対象カードの `listId` に相当するリストが `boardId` 経由で解決できない」 という異常系のみとする。
  - 案 B: リスト削除 / ボード削除では active カードのみカスケード削除し、archived / deleted カードは孤児として保持する。孤児カードのアクセス経路 (`GET /api/boards/{boardId}/archived-cards` の対象か / 復元先はどうするか) を追加定義する。
- 確認が必要な判断点
  - どちらを採るか。教材としては案 A が単純で AC も書きやすい。案 B を採るなら「孤児 archived / deleted カードの一覧経路と復元 UI」 を追加設計する必要が生じる。

### 抜漏-3 [Middle] active カードに対する直接完全削除の AC が無い

### 抜漏-4 [Middle] archived → soft delete 経路での `archivedAt` の扱いが不明

- 問題箇所
  - line 118「対象カードの `status` を `deleted` に、`deletedAt` を現在時刻に更新する。`archivedAt` は保持する」
  - line 256「アーカイブ済みカードに対する soft delete: 遷移として許可、`status = deleted` へ更新。」
- 問題の理由
  - line 118 は FR-003-1「カードを削除する」 の中で active カードから soft delete する場合の記述に見えるが、archived カードから soft delete する場合も「`archivedAt` を保持」 で良いのか明示なし。
  - line 256 の境界条件では「`status = deleted` へ更新」 とだけあり、`archivedAt` に触れていない。
  - archived → deleted 遷移後に復元 API を呼んだ場合、「元 `listId` に戻す」 のは自然だが、「archived / deleted の履歴を持っていた」 情報 (`archivedAt`) が復元後にも残るのかも未定義。
- 修正案
  - line 118 を「対象カードの `status` を `deleted` に、`deletedAt` を現在時刻に更新する。`archivedAt` は現在の値をそのまま保持する (active から soft delete した場合は `null` のまま、archived から soft delete した場合はアーカイブ時刻を保持)」 に書き換える。
  - 復元 API の記述 (line 108-112 / 124-129) に「復元時の `archivedAt` / `deletedAt` はいずれも `null` に戻す」 を追加。
- 確認が必要な判断点
  - archived → deleted → restore と遷移した後、`archivedAt` を保持するか (履歴として残す) / null に戻すか (完全に active に戻す)。教材としては「復元時は両者とも null」 が単純で AC も書きやすい。

### 矛盾-1 [High] FR-002-1 と FR-002-2 で復元時の配置ルールが食い違う

- 問題箇所
  - line 104 (FR-002-1) 「`order` は保持しておき復元時に元位置を試みる」
  - line 110 (FR-002-2) 「対象カードを復元先リストの末尾に配置する」
- 問題の理由
  - FR-002-1 の「元位置を試みる」 と FR-002-2 の「末尾に配置する」 は排他的な挙動。同じ「アーカイブ済みカードの復元」 について 2 種類の記述があるため、実装分岐が起きる。
- 修正案
  - 「復元時は常に末尾配置」 に統一 (FR-002-1 の「元位置を試みる」 記述を削除)。理由 = FR-003-2 の削除済み復元も末尾配置 (line 128) で統一されており、UX として一貫する。
- 確認が必要な判断点
  - 「末尾配置に統一」 で確定して良いか。ハンズオンとしてはこれで実装単純化。

### 矛盾-2 [Middle] 復元前 status に応じて自動判定する経路と、AC 側の記述の齟齬

- 問題箇所
  - line 162「`POST /api/cards/{cardId}/restore` は復元前の `status` (`archived` / `deleted`) に応じてどちらの復元も行う。復元経路の分岐はサーバー側で自動判定する」
  - AC line 184「アーカイブ一覧から復元を実行すると、対象カードは元リストの末尾に配置され、既定の一覧に戻る」
  - AC line 186「削除済み一覧から復元を実行すると、対象カードは元リストの末尾に配置され、既定の一覧に戻る」
- 問題の理由
  - サーバー側自動判定なら、AC の分岐条件は「復元前の status」 で書くべき。「アーカイブ一覧 / 削除済み一覧から」 は UI 経路の分岐であり、API 側は関知しない。AC が UI 経路依存で書かれていると、API テスト単体では検証しにくい。
- 修正案
  - AC を「archived 状態のカードに対して `POST /api/cards/{cardId}/restore` を呼ぶと、`status = active` に戻り、元リストの末尾に配置される」「deleted 状態のカードに対して `POST /api/cards/{cardId}/restore` を呼ぶと、`status = active` に戻り、元リストの末尾に配置される」 に書き換える。
- 確認が必要な判断点
  - AC を API レベルの検証条件に統一するか、UI 経路 (どの画面から実行するか) を残すか。教材としては API レベルで書き、UI 経路は「画面」 セクションに残す形が明快。

## 観点4: テスト不能項目

### テスト不能-1 [Middle] 操作ログの記録が AC に含まれているが検証条件が不明

- 問題箇所
  - AC line 197「アーカイブ、soft delete、復元、完全削除の各操作は操作ログに記録される」
  - `§ 運用 (操作ログ)` line 314 「ログの保存先と保存形式は設計工程で決める」
- 問題の理由
  - ログの保存先と形式が未確定 (line 314) の状態で、AC line 197 の「記録される」 を Vitest で検証する経路が無い。実装時に「ログ関数が 1 回呼ばれたことをスパイで検証」 のようなプロキシテストを書くことは可能だが、AC からその方針が読み取れない。
- 修正案
  - AC line 197 を分解して「各操作 API の成功応答直後に、`§ 運用 (操作ログ) § 操作ログ` に定義された全フィールド (`操作種別` / `対象リソース識別子` / `対象ボード識別子` / `操作ユーザー識別子` / `遷移前状態` / `遷移後状態` / タイムスタンプ) を含むログエントリが 1 件追加される」 に書き換える。
  - 検証経路として「ログ関数呼出のモック検証」 を許容する旨を `§ 運用` に追記する。
- 確認が必要な判断点
  - ログ関数呼出のモック検証で AC を満たすと合意するか、実際のログ保存先 (ファイル / 標準出力 / DB) まで確定させた上でエンドツーエンド検証するか。教材としてはモック検証で十分。

### テスト不能-2 [Low] `§ 同時更新時の扱い § 具体挙動` の同時発火挙動がテスト不能

- 問題箇所
  - line 320-322「同一カードに対するアーカイブ / 復元 / soft delete が同時に発火した場合、DB 上の状態遷移が有効な操作 (状態遷移として正当) のみ成功し、遷移が不整合な操作は `422` を返す」
- 問題の理由
  - 「同時発火」 の再現テストは通常の単体 / 統合テストでは書きにくく、意図的な race condition テストが必要になる。Vitest のフィクスチャで同時実行の順序を制御する必要があるが、その挙動が仕様書に反映されていないと、実装時に「テストできないから省略」 になりがち。
- 修正案
  - `§ 同時更新時の扱い` の末尾に「本 spec の対象範囲では、同時発火の再現テストは書かない (last-writer-wins の受け入れ)。将来的な楽観的ロック導入時にテスト経路を追加する」 を明記する。
  - あるいは「同時発火の代替として、直列に 2 回同じ操作を呼んだ場合の挙動を AC でカバーする」 とし、AC line 194-196 (再アーカイブ / 再 soft delete / active への復元) がその代替であると宣言する。
- 確認が必要な判断点
  - 教材として「同時発火の記述を残す」 か「直列 2 回呼び出しに置き換える」 か。教材としては後者が現実的。

## 全体総括

`spec/004` の設計は既存 3 仕様 (001 / 002 / 003) を追補する形として整合性の宣言がしっかり書かれており、状態遷移表 / API 一覧 / 権限マトリクスの分離も明確。ハンズオン教材として実装対象を絞る意図もよく通っている。

一方で以下 3 点は「実装時に必ず分岐する」 論点なので、実装工程に入る前に決めきる価値がある。

- 復元時の配置ルール (末尾配置 vs 元位置優先) → 矛盾-1 / 曖昧-1
- archived / deleted カードに対する既存 `GET` / `PATCH` API の挙動 → 抜漏-1
- リスト削除 / ボード削除時の archived / deleted カードのカスケード扱い → 抜漏-2
