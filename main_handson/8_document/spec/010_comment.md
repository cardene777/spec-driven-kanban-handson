# コメント機能の仕様

## 概要

本 file はカード (Card) に対するコメント (Comment) 機能の仕様を定義する。
対象操作はコメントの投稿、一覧取得、削除の 3 種類とする。
共通ルールは `spec/000_shared_rules.md`、カード基本仕様は `spec/003_cards.md`、カード詳細モーダルの構成は `spec/005_card_detail.md` を参照する。
`constitution.md § 用語集` の「コメント (Comment)」を対象とし、`constitution.md § 権限ポリシー` に従って権限境界を定義する。

## 既存仕様との関係

- `spec/005_card_detail.md § 対象データ § Comment エンティティ` および `§ 操作: コメント投稿 / § 操作: コメント削除` は本 spec の初期案 (下敷き) である。本 spec が Comment 機能の SSOT となり、以降 Comment に関する規定は本 file に集約する。
- 本 spec と `spec/005_card_detail.md` の Comment 関連記述が矛盾した場合は、本 spec を優先する。
- 本 spec は以下 3 点で `spec/005_card_detail.md` を上書きする。
  - 一覧の並び順 = `spec/005_card_detail.md` は `createdAt` 昇順としていた。本 spec では投稿日時 (`createdAt`) の降順に変更する (最新コメントを一覧先頭に表示する)。
  - コメント本文の保存形式 = 保存時に HTML エスケープを行い、DB には特殊文字を `&amp;` / `&lt;` / `&gt;` / `&quot;` / `&#39;` に置換した文字列を保持する (`§ 非機能要件 § セキュリティ`)。
  - コメント編集は本 spec の対象外 (投稿・一覧取得・削除の 3 操作のみを対象とする)。

## 対象データ

### Comment エンティティ

| フィールド | 型 | 説明 |
|---|---|---|
| `id` | 文字列 | コメントを一意に識別する ID |
| `cardId` | 文字列 | 所属するカードの ID |
| `authorId` | 文字列 | 投稿者ユーザー ID |
| `body` | 文字列 | コメント本文 (保存後の HTML エスケープ済み文字列、元文字列で 1〜2000 文字) |
| `createdAt` | ISO8601 UTC | 投稿日時 |
| `updatedAt` | ISO8601 UTC | 更新日時 (本 spec では投稿時のみ設定、以降変化しない) |

- コメントの `id` はグローバル一意とする。
- コメントは物理削除 (soft delete しない)。復元は行わない。
- 投稿者ユーザー (`authorId`) はサーバー側で現在ログイン中のユーザーから決定する。クライアントは指定できない。
- コメント編集は本 spec の対象外 (`§ 未決事項`)。

## 機能要件

### FR-01: カードにコメントを投稿する

- カード詳細モーダルの投稿フォームから実行する。
- 入力項目は `body` のみ (トリム前の元文字列で 1〜2000 文字)。
- 投稿後、対象カードのコメント一覧の先頭に追加され、`createdAt` は現在時刻となる (`§ 非機能要件 § 一覧の並び順`)。
- 投稿者は現在ログイン中のユーザー (`authorId` はサーバー側で決定)。
- 投稿時、対象カードの `updatedAt` は更新しない (カード本体の変更ではないため)。
- 保存前に `body` を HTML エスケープする (`§ 非機能要件 § セキュリティ`)。

観測可能な完了条件

- [ ] `POST /api/cards/{cardId}/comments` に `member` 以上のユーザーが `body` = 1〜2000 文字を送ると `201` と作成された `Comment` オブジェクトが返る。
- [ ] 作成された `Comment` の `authorId` は現在ログイン中のユーザー ID と一致する。
- [ ] 保存された `body` は、投稿時に HTML エスケープされた文字列である。
- [ ] 対象カードの `updatedAt` は投稿の前後で変化しない。

### FR-02: カードのコメント一覧を取得する

- カード詳細モーダルを開く時、およびコメントの投稿・削除後にサーバー再取得で更新する。
- 一覧は `createdAt` の降順を第一キー、同時刻 (ミリ秒レベル一致) は `id` 昇順を第二キーで返す (`§ 非機能要件 § 一覧の並び順`)。
- 一覧のレスポンス形式は `spec/000_shared_rules.md § 一覧 API のレスポンス構造` に従う。
- 一覧はページネーションを行わず、全件を返す (本 spec の初期実装)。

観測可能な完了条件

- [ ] `GET /api/cards/{cardId}/comments` に `viewer` 以上のユーザーがアクセスすると `200` と `{ items: Comment[] }` が返る。
- [ ] レスポンスの `items` は `createdAt` 降順、同時刻時は `id` 昇順で並ぶ。
- [ ] コメント 0 件のカードは `{ items: [] }` を `200` で返す。

### FR-03: 自分のコメントを削除する

- カード詳細モーダルのコメント一覧の各行から削除導線を実行する。
- 削除は明示的な確認 (確認ダイアログ等) を伴う。UI 詳細は `ui-design/` で決める。
- 対象コメントの投稿者本人 (`authorId = 現在ユーザー`) かつ `member` 以上のロールを持つ場合に許可する。
- 削除は物理削除。

観測可能な完了条件

- [ ] 投稿者本人 (`member` 以上) が `DELETE /api/comments/{commentId}` を呼ぶと `204` (body なし) が返る。
- [ ] 削除後、`GET /api/cards/{cardId}/comments` のレスポンスから当該コメントが除外される。

### FR-04: owner が他人のコメントを削除する

- 対象ボードの `owner` は、投稿者を問わずコメント一覧の各行から削除できる。
- 削除経路は FR-03 と同一 (`DELETE /api/comments/{commentId}`)。
- 削除は物理削除。

観測可能な完了条件

- [ ] `owner` が他ユーザーの投稿コメントに対して `DELETE /api/comments/{commentId}` を呼ぶと `204` が返る。
- [ ] `member` が他ユーザーの投稿コメントに対して同 API を呼ぶと `403` が返る。

## API

| メソッド | パス | 用途 | 必要権限 |
|---|---|---|---|
| `GET` | `/api/cards/{cardId}/comments` | 指定カードのコメント一覧を取得 | 対象ボードの `viewer` 以上 |
| `POST` | `/api/cards/{cardId}/comments` | 指定カードにコメントを投稿 | 対象ボードの `member` 以上 |
| `DELETE` | `/api/comments/{commentId}` | コメントを削除 | 投稿者本人 (`member` 以上) または対象ボードの `owner` |

- レスポンス形式と認証チェック順序は `spec/000_shared_rules.md` に従う。
- 一覧 API のレスポンスは `{ items: Comment[] }`、投稿 API のレスポンスは作成された `Comment` オブジェクトを `201` で返す。
- `POST /api/cards/{cardId}/comments` のリクエスト body は `{ "body": <文字列> }`。
- `DELETE /api/comments/{commentId}` は成功時に `204` (body なし) を返す。

## 受入条件

FR ごとの完了条件は `§ 機能要件` の各 FR に記載する。以下は FR を横断する統合条件。

- [ ] `member` が `body` = 1 文字を投稿すると `201` と作成された `Comment` が返る (下限)。
- [ ] `member` が `body` = 2000 文字を投稿すると `201` と作成された `Comment` が返る (上限ちょうど)。
- [ ] `member` が `body` = 2001 文字を投稿すると `422` (`body`, `too_long`) が返り、コメントは追加されない。
- [ ] `member` が `body` = 空文字を投稿すると `422` (`body`, `required`) が返る。
- [ ] `member` が `body` = 空白のみ (トリム後 0 文字) を投稿すると `422` (`body`, `required`) が返る。
- [ ] `member` が `body` が文字列型でない値を投稿すると `422` (`body`, `invalid_type`) が返る。
- [ ] 投稿された `body` に `<script>alert(1)</script>` を含むと、DB 保存値は `&lt;script&gt;alert(1)&lt;/script&gt;` にエスケープされている。
- [ ] `viewer` が `GET /api/cards/{cardId}/comments` を呼ぶと `200` が返る。
- [ ] `viewer` が `POST /api/cards/{cardId}/comments` を呼ぶと `403` が返る。
- [ ] `viewer` が `DELETE /api/comments/{commentId}` を呼ぶと `403` が返る。
- [ ] 投稿者以外の `member` が他ユーザーのコメントを削除しようとすると `403` が返る。
- [ ] `owner` が他ユーザーの投稿コメントを削除すると `204` が返る。
- [ ] 未ログインユーザーが本 spec のいずれの API を呼んでも `401` が返る。
- [ ] 存在しない `cardId` を指定した全 API 呼出で `404` が返る。
- [ ] 存在しない `commentId` を指定した `DELETE` は `404` が返る。
- [ ] 対象カードが所属するボードの閲覧権限を持たないユーザーが全 API を呼ぶと `404` が返る (存在有無の露出を防ぐ)。
- [ ] コメント 0 件のカードは `GET` で `{ items: [] }` を `200` で返す。
- [ ] 一覧 API のレスポンスは `createdAt` 降順で並ぶ (最新が先頭)。
- [ ] コメント投稿・削除に成功すると、操作ログに `event` / `cardId` / `boardId` / `actorId` / `commentId` が記録される。

## 異常系

`spec/000_shared_rules.md § HTTP ステータスコード` と `§ Route Handler の入口チェック順序` に従う。本 spec で追加のステータスコードは用いない (401 / 403 / 404 / 422 の 4 種のみ)。

### 認証、権限、存在チェック

| 状況 | ステータス | 補足 |
|---|---|---|
| 未ログインで本 spec の API 呼出 | `401` | 全 API 共通 |
| 存在しない `cardId` を指定 | `404` | 一覧 / 投稿 API |
| 存在しない `commentId` を指定 | `404` | 削除 API |
| 閲覧権限 (`viewer` 以上) のないボード配下のカード / コメントを指定 | `404` | 存在有無を漏らさないため `404` に統一 |
| `viewer` ロールが投稿 API (`POST`) を呼ぶ | `403` | 認証済み、閲覧可の状態が前提 |
| `viewer` ロールが削除 API (`DELETE`) を呼ぶ | `403` | 認証済み、閲覧可の状態が前提 |
| 投稿者以外の `member` が他ユーザーのコメントを削除しようとする | `403` | 投稿者本人または `owner` のみ削除可 |

### バリデーションエラー

| 状況 | ステータス | フィールド | メッセージ例 |
|---|---|---|---|
| `body` 未指定 (投稿 body 空) | `422` | `body` | `required` |
| `body` が空文字 | `422` | `body` | `required` |
| `body` がトリム後 0 文字 (空白のみ) | `422` | `body` | `required` |
| `body` が 2001 文字以上 (元文字列基準) | `422` | `body` | `too_long` |
| `body` が文字列型でない | `422` | `body` | `invalid_type` |

### 画面レベル

- コメント投稿 API が `422` を返した場合、投稿フォーム直下にフィールド別エラーメッセージを表示する (`body: required` / `body: too_long` / `body: invalid_type`)。
- コメント投稿 API が `403` / `401` を返した場合、コメント領域内に「操作権限がありません」 または「ログインが必要です」 相当の表示を行う (文言は `ui-design/`)。
- コメント削除 API が `403` を返した場合、「操作権限がありません」 相当の表示を行い、対象コメント行は一覧に残す。
- コメント削除 API が `404` を返した場合 (他ユーザーが同時に削除した等)、コメント領域を再取得して最新状態に整合させる。

## 境界条件

### `body` の長さ (元文字列基準、HTML エスケープ前の文字数)

- 1 文字 (下限ちょうど): 受け付ける。
- 2000 文字 (上限ちょうど): 受け付ける。
- 2001 文字: `422` (`too_long`) を返す。
- 0 文字 (空文字): `422` (`required`) を返す。
- トリム後 0 文字 (空白のみ): `422` (`required`) を返す。
- トリム前の先頭・末尾の空白: 保存時にトリムせず、元文字列のまま HTML エスケープして保存する (本文中の連続空白も保持)。

### `body` の HTML エスケープ後の長さ

- HTML エスケープ後の文字列が 2000 文字を超えても、元文字列が 2000 文字以下であれば `422` としない (上限判定は元文字列基準)。
- 例 = `body = "<".repeat(2000)` (元 2000 文字) → 保存値は `"&lt;".repeat(2000)` (8000 文字) となる。API は `201` を返す。

### 一覧

- コメント 0 件: 一覧 API は `{ items: [] }` を `200` で返す。
- 同一 `createdAt` (ミリ秒レベルで一致) のコメント: `id` 昇順で解決する (降順キーは `createdAt` のみ)。
- 一覧の並び順は `createdAt` 降順 (最新が先頭)、同時刻は `id` 昇順。

### 存在しないリソース

- 存在しない `cardId` を指定した一覧・投稿 API: `404` を返す。
- 存在しない `commentId` を指定した削除 API: `404` を返す。

### ロール別の視認性

- 対象ボードの `viewer`: `GET` は `200` で成功、`POST` / `DELETE` は `403`。
- 対象ボードの `member` (投稿者本人): `GET` / `POST` / 自分の `DELETE` すべて許可。他ユーザーの `DELETE` は `403`。
- 対象ボードの `owner`: `GET` / `POST` / 全 `DELETE` すべて許可。
- 対象ボードに所属しないユーザー: `404` を返す (閲覧権限がないため存在有無を漏らさない)。

## バリデーション

| フィールド | ルール |
|---|---|
| `cardId` (URL パラメータ) | 文字列。存在しないと `404`。 |
| `commentId` (URL パラメータ) | 文字列。存在しないと `404`。 |
| `body` (`POST` body) | 文字列 (`invalid_type` 判定は他フィールドに先行)。トリム後 1〜2000 文字。トリム後 0 は `required`、2001 以上 (元文字列基準) は `too_long`。 |

- `POST` API では `id` / `authorId` / `cardId` / `createdAt` / `updatedAt` はクライアントから受け取らない (サーバー側で決定する)。
- `DELETE` API で受け付けるのは URL パラメータの `commentId` のみ (body なし)。
- `GET` API はクエリパラメータを受け取らない (フィルタ、ページネーションは対象外)。

## 権限境界

`spec/000_shared_rules.md § 権限マトリクス` と本 spec 追加操作を統合した表。

| 操作 | 必要権限 | 権限不足時の挙動 |
|---|---|---|
| コメント一覧取得 (`GET /api/cards/{cardId}/comments`) | 対象ボードの `viewer` 以上 | 未ログイン `401`、閲覧不可 `404` |
| コメント投稿 (`POST /api/cards/{cardId}/comments`) | 対象ボードの `member` 以上 | 未ログイン `401`、`viewer` は `403`、閲覧不可 `404` |
| コメント削除 (`DELETE /api/comments/{commentId}`) | 投稿者本人 (`member` 以上) または対象ボードの `owner` | 未ログイン `401`、削除権限なし `403`、閲覧不可 `404` |

- 削除の権限判定は 2 段構造とする。
  1. `assertBoardAccess(actorId, boardId, "viewer")` で閲覧権限を判定 (閲覧不可は `404`)。
  2. その上で「(`authorId = actorId` かつ actor のロール ≥ `member`) または actor のロール = `owner`」 のいずれかを満たさない場合に `403` を返す。
- 投稿者本人であっても、投稿後にロールが `viewer` に降格した場合は削除できない (現時点のロールが `member` 以上である必要がある)。
- 自分自身が投稿したコメントの削除も、上記の必要権限に従う (自身削除の特別扱いはしない)。

## 非機能要件

`spec/000_shared_rules.md § 非機能要件` に従う。本 spec 固有の要件は次の通り。

### 性能

- コメント一覧 API は一覧 API として P95 200ms 以内。
- コメント投稿 / 削除 API は書き込み API として P95 300ms 以内。

### 一覧の並び順

- コメント一覧 API は `createdAt` の降順を第一キー、`id` の昇順を第二キーで返す。
- 本 spec の並び順規定は `spec/000_shared_rules.md § 一覧 API のレスポンス構造` の「`order` 昇順を第一キー」 の一般規則の例外とする (Comment には `order` フィールドを持たせず、時系列で最新が先頭に来る表示を優先する)。

### セキュリティ (HTML エスケープ)

- コメント本文 `body` は保存時に HTML エスケープを行う。対象文字と置換後は以下の通り。

| 対象文字 | 置換後 |
|---|---|
| `&` | `&amp;` |
| `<` | `&lt;` |
| `>` | `&gt;` |
| `"` | `&quot;` |
| `'` | `&#39;` |

- エスケープの実施タイミングは Route Handler での保存直前とする (バリデーション後、`prisma.comment.create` 呼び出し直前)。
- 一覧取得時はエスケープ済みの文字列をそのまま返す (二重エスケープしない)。
- 表示側 (`ui-design/` および `design/010_comment.md § UI` 相当) は React JSX の自動エスケープに任せる。DB 側と表示側で二重防御となる。
- 長さ判定 (`§ バリデーション`) は元文字列 (エスケープ前) の文字数で行う。

### 運用 (操作ログ)

- コメント投稿・削除の各操作について、操作種別 (`comment.create` / `comment.delete`)、対象識別子 (`commentId`)、対象カード識別子 (`cardId`)、対象ボード識別子 (`boardId`)、操作ユーザー識別子 (`actorId`)、タイムスタンプを操作ログに残す。
- 削除操作では投稿者 (`authorId`) と削除者 (`actorId`) を分けて記録する (owner による他者コメント削除の追跡)。
- エラーレスポンスを返した場合、ステータス、エラーコード、対象識別子 (取得できる範囲)、操作ユーザー識別子をログに記録する。

## 未決事項

- コメント編集機能は本 spec の対象外。将来別 spec で扱う。
- コメントに対する Markdown レンダリング、メンション (`@user`)、リアクション、返信は本 spec の対象外。
- コメント一覧のページネーションは本 spec の対象外 (初期実装は全件返却)。
- 保存時 HTML エスケープの対象外文字 (絵文字・多バイト文字) はエスケープ不要とし、エスケープ規則は `§ 非機能要件 § セキュリティ` の 5 対象文字に限る。
- コメントに対する通知 (メンションユーザーへのメール、in-app 通知) は本 spec の対象外。
- コメント削除後の物理削除以外の代替 (soft delete / 履歴保持) は本 spec の対象外。
