# /implement

仕様と設計をコードに落とす、実装コードを書くスキル。
`constitution.md` の技術スタック、規約、権限ポリシー、非機能要件を読み、対象プロジェクトの既存構成に合わせて実装する。
本スキルは 2 つのモードで動く。

- 仕様駆動モード: `spec/*.md` と `design/*.md` から実装とテストを起こす。
- テスト先行モード: `/tdd` が先に書いた失敗テスト (Red) を入力に取り、それを通す最小実装 (Green) を書き、テストを保ったまま整理する (Refactor)。この場合は新規テストを起こさず、既存の失敗テストを通すことに集中する。

## トリガー条件

- 「この設計を実装して」、「この仕様と設計を実装して」
- `spec/*.md` と `design/*.md` が揃ったあと
- `/tdd` で失敗テストを書いた直後（テスト先行モード）

## 入力

- `constitution.md`
- 対象の `spec/*.md`
- 対応する `design/*.md`
- 対応する `design/*_ui.md`（存在する場合）
- `/tdd` が書いた失敗テスト（テスト先行モードの場合）
- `.context/tdd/cycles.md`（テスト先行モードの場合。`/tdd` が記録した Red の一覧と、Green にする対象受入条件）
- 既存コード
- 既存のテスト・ビルド・lintコマンド

## 出力

仕様と設計に従って、必要なファイルを生成または更新する。

- データモデルまたは永続化層
- APIやサーバー側処理
- UIまたは画面側処理
- 認証・認可・ログなどの共通処理
- 対応するテスト

各ファイルには、必要に応じて対応する仕様要件IDと設計セクション参照を残す。

## 作業手順

1. **入力ファイル確認**

   `constitution.md`、対象 `spec/*.md`、対象 `design/*.md` を読み込む。対応する `design/*_ui.md` がある場合は、コンポーネント構成とアクセシビリティ要件も読み込む。テスト先行モードでは `.context/tdd/cycles.md` を読み、`/tdd` が記録した失敗テストと対象受入条件から Green にするスコープを確定する。
2. **既存コード確認**

   既存コード、ディレクトリ構成、実行コマンドを確認する。
3. **実装対象の整理**

   仕様と設計から、作成・更新するファイルを列挙する。
4. **共通処理の確認**

   認証、認可、ログ、エラー処理、バリデーションなどの共通処理が必要か確認する。
5. **コード生成**

   対象プロジェクトの技術スタックに合わせて実装する。テスト先行モードでは、`/tdd` が書いた失敗テストを通す最小実装を書く（Green）。
6. **テスト対応**

   仕様駆動モードでは、正常系・異常系・権限境界・境界条件のうち仕様で求められるテストを生成する。テスト先行モードでは新規テストを起こさず、既存の失敗テストが PASS することを確認する。
7. **リファクタ**

   テストが通る状態を保ったまま、重複・命名・責務を整える（Refactor）。振る舞いは変えない。
8. **静的検証**

   `package.json`、テストランナー設定、CI定義を読み、定義済みの `lint`、`typecheck`、`test`、`build` を実行する。`typecheck` が無いTypeScriptプロジェクトでは `npx tsc --noEmit` を実行する。実行しなかった検証は、理由とともに最後の報告へ残す。
9. **失敗時対応**

   失敗したら修正して再実行する。繰り返し失敗する場合はユーザーに報告する。

## コード生成の方針

- フレームワークやORMをスキル内で固定しない
- 認証・認可ヘルパーの名前をスキル内で固定しない
- 既存のプロジェクト構成を優先する
- 仕様にない機能をついでに追加しない
- エラー処理は `constitution.md` と設計に従う
- プロジェクトにデザインシステムがある場合、UI は hex 直書きや素の色クラス・素の `<button>` / `<input>` を使わず、既存のトークン参照と共通コンポーネント（shadcn 等）に合わせる。ダイアログに領域を足す場合は操作ボタン（footer）を本文の途中に挟まず最下部に保つ

## 注意事項

- 仕様にない権限チェックを勝手に追加しない。仕様変更が必要なら `/spec` に戻る
- テスト先行モードでは、テストを通すためにテスト側を書き換えない。実装で通す
- 機密情報や個人情報をログに直接含めない
- テストコマンドやlintコマンドは対象プロジェクトの設定から判断する
