# /spec-review

仕様を4つの観点で確認するスキル。
`constitution.md` と関連仕様を参照し、曖昧表現、抜け漏れ、矛盾、テスト不能項目の候補をレビューレポートにまとめる。レポートの採否は人が判断する。

## トリガー条件

- 「この仕様をレビューして」、「{機能名}の仕様の曖昧さを検出して」
- `spec/*.md` を出力した直後
- 実装に入る前の最終確認

## 入力

- `constitution.md`（用語集・権限ポリシー参照用）
- レビュー対象の `spec/*.md`
- `spec/000_shared_rules.md`（並び順・カスケード削除などの横断共有ルール。存在する場合は必ず突合する）
- 関連する既存 `spec/*.md`（横断整合チェック用）

## 出力

`review/{機能ID}_{機能名}_spec_review.md` を生成する。複数仕様を一括レビューする場合は範囲を表す `review/{開始ID}_{終了ID}_{まとめ名}_spec_review.md`（例 `review/011_013_auth_invite_permissions_spec_review.md`）とする。
レビューレポートは `review/` 配下に置き、`spec/` には出力しない。`spec/` を汚さないことで、後続の `/spec` の連番採番（`spec/` の最大番号+1）がレビューファイルを誤って拾わないようにする。

## 深刻度の3段階

各指摘に深刻度を付け、High から順に対応する。

- High: 実装が分岐する / 仕様に反する / 権限やセキュリティの穴 / 読者が手順どおり進めて詰まる
- Middle: 挙動は観測できるが仕様として曖昧 / 受入条件に落とし込めていない
- Low: 表現・整合ノイズ / 将来改善の範囲

## 4つのレビュー観点

### 観点1: 曖昧表現の検出

- 主観的表現
- 数値で測れない形容
- 不定量表現
- 留保表現

検出したら、`constitution.md` の数値目標または具体的な条件への書き換えを提案する。

### 観点2: 抜け漏れの検出

- 機能要件
- 異常系
- 境界条件
- バリデーション
- 非機能要件
- 権限境界
- 用語参照

足りないセクションがあれば、必要な追記を提案する。

### 観点3: 矛盾の検出

- 仕様内の条件矛盾
- 関連仕様との用語やAPI責務のずれ
- `constitution.md` の権限ポリシーや用語集との不一致

どちらが正しいか判断できない場合は、ユーザー確認を挟む。

### 観点4: テスト不能項目の検出

- 主観的判断が必要な要件
- 観測不能な内部状態への言及
- 環境依存な要件
- 副作用が明示されていない処理

テスト可能な形への書き換えを提案する。

## 作業手順

1. Constitution確認
   `constitution.md` をReadで読み込む。
2. レビュー対象確認
   レビュー対象の `spec/*.md` をReadで読み込む。
3. 関連spec確認
   関連する既存 `spec/` をGlobで探し読み込む。
4. 観点別チェック
   4つの観点でチェックし、各指摘に深刻度（High/Middle/Low）を付ける。
5. レポート生成
   出力テンプレートに従ってレビューレポートを生成し、全体総括と次のアクション候補まで書く。
6. 修正方針確認
   ユーザーにレビュー結果を提示し、High から順に修正方針を確認する。

## 注意事項

- レビュー結果は元仕様を直接書き換えず、まず別ファイルに出す
- 修正判断が必要な箇所はAIだけで決めない
- スキル内に特定ドメインのロール名や用語を固定しない
