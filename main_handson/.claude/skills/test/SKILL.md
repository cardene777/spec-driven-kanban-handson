# /test

仕様から4軸で網羅的にテストケースを導出するスキル。
本章用の`/spec`が出力した `spec/*.md` を入力として、正常系・異常系・境界条件・状態遷移の4軸でテストケースを列挙し、既存テストファイルに追記する。

## トリガー条件

- 「{機能名} のテスト範囲を広げて」、「異常系・境界条件を網羅して」
- `/tdd` のRed-Green-Refactorサイクルが終わったあと
- リファクタ前に「カバー範囲を広げて安全網を作りたい」とき
- バグ修正後に「同じパターンの抜けを境界条件で確認したい」とき

## 入力

- `constitution.md`（非機能要件・権限ポリシー参照用）
- 対象の`spec/*.md`（4軸の導出元）
- 既存テストファイル（既存ケースの保持・追記位置の判定用）
- 対象実装ファイル（仕様と実装の差分検出用）

## 出力

既存テストファイルに以下の構造で追記する。

```typescript
describe('{機能名} - 正常系', () => {
  // 既存ケース（変更なし）
  it('既存ケース 1', () => { /* /tdd で書いたコード */ })

  // 新規追加
  it('正常系ケース 2', () => { /* /test が追加 */ })
  it('正常系ケース 3', () => { /* /test が追加 */ })
})

describe('{機能名} - 異常系', () => {
  // 既存ケース + 新規追加
})

describe('{機能名} - 境界条件', () => {
  // 新規追加
})

describe('{機能名} - 状態遷移', () => {
  // 新規追加
})
```

合わせて、テストヘルパー（`buildRequest` `seedAssignees` など）が必要なら別ファイルに切り出す。

サイクル全体が終わると、最後に以下のサマリーを出力する。

```markdown
# /test実行サマリー

対象機能: {機能名}
対象spec: spec/{機能ID}_{機能名}.md
対象テスト: {テストファイルパス}

## 追加件数

| 軸 | 既存 | 追加 | 合計 |
|---|---|---|---|
| 正常系 | {n} | {n} | {n} |
| 異常系 | {n} | {n} | {n} |
| 境界条件 | {n} | {n} | {n} |
| 状態遷移 | {n} | {n} | {n} |
| 合計 | {n} | {n} | {n} |

## テスト実行結果

{PASS / FAILの内訳}

## 検出した仕様と実装の差分

- {テストケース名}: {Expected} vs {Received}
  - 仕様: {仕様の該当箇所}
  - 実装: {実装の該当箇所}
  - 推奨対応: {実装を直す / 仕様を直す / 保留}
```

## 4軸の判定基準

各軸でテストケースを列挙する基準を以下にまとめる。

### 正常系（ユースケーステスト）

- ACごとに主経路1件
- ACごとに代替経路（異なるロール・異なる入力パターン）1〜2件
- 対象ロール: owner / member / viewer + 自分自身

### 異常系（エラー推定）

- 入力エラー（バリデーション失敗、型不一致、必須欠落）: 1〜2件
- 権限エラー（未認証401、権限不足403）: 各1件
- 整合性エラー（重複409、関連不在404、上限超過422）: 各1件

### 境界条件（境界値分析）

- 件数の最小（0件、1件）
- 件数の最大（上限ぎりぎり、上限超過 +1）
- 文字列の最大（最大長、最大長 +1、空、null）
- 数値の境界（最小値、最大値、最小値 -1、最大値 +1）

### 状態遷移（状態遷移テスト）

- 状態A → 状態Bへの遷移を「遷移前 / 遷移操作 / 遷移後」で観測
- 主要遷移ごとに1件（追加・更新・削除など）
- 単体テストで複数APIを組み合わせるシーケンス検証も含む

## テスト記述スタイル

本書はVitestを前提とする。Jest / Playwrightに差し替えるときは以下を読み替える。

| 項目 | Vitest | Jest | Playwright |
|---|---|---|---|
| import | `from 'vitest'` | (グローバル) | `from '@playwright/test'` |
| describe / it | 同じ | 同じ | `test.describe` / `test` |
| expect | 同じ | 同じ | 同じ |
| beforeEach | 同じ | 同じ | `test.beforeEach` |

スキル内ではVitestのスタイルを標準とし、ユーザーが他フレームワークを使っていたら最初に確認する。

## 作業手順

1. 仕様確認
   `constitution.md` と対象 `spec/*.md` を読み込む。
2. 実装とテスト確認
   対象実装ファイル（`{対象}.ts`）と既存テストファイル（`{対象}.test.ts`）を読み込む。
3. 既存ケース分類
   既存テストケースを軸ごとに分類する。正常系n件、異常系n件などを数える。
4. 追加ケース列挙
   仕様の各セクションを4軸でスキャンし、追加すべきケースを列挙する。
5. 追加ケース承認
   AskUserQuestionで追加ケース一覧をユーザーに提示し承認を得る。
6. describeブロック作成
   テストファイルに4軸のdescribeブロックを作成する。既存ケースは保持する。
7. 追加ケース追記
   追加ケースをそれぞれの軸のdescribeブロックに追記する。
8. テストヘルパー切り出し
   テストヘルパーが必要なら別ファイルに切り出す。
9. テスト実行
   テストを実行してPASS / FAILを確認する。
10. FAIL時確認
   FAILがあれば仕様と実装の差分としてAskUserQuestionで対応方針を確認する。
11. サマリー出力
   最後にサマリーを出力する。

## 軌道修正の判断ポイント

| 兆候 | 推奨される対応 |
|---|---|
| 追加ケースが1機能あたり20件超 | 仕様の分割を `/spec-review` に戻って検討 |
| 4軸のうち1軸が0件のまま | 仕様にその軸の記述が無い可能性、`/spec-review` で確認 |
| FAILが5件超 | 実装が仕様から大きくずれている、`/design` に戻る判断も視野 |
| カバレッジが80% を切る | 4軸以外（並行性・パフォーマンス）の追加が必要 |

## 注意事項

- 既存テストケースを上書き・削除しない（必ず追記）
- 4軸のうち、仕様に該当する記述が無い軸は0件のままで構わない
- ケース名は仕様の文言を流用し、テストコードと仕様の対応を明確にする
- テストヘルパーは個別ファイルに切り出し、テストファイル本体を肥大化させない
- カバレッジ100% を目標にしない（80% を下回ったら抜けを疑う、が目安）
- FAILを「実装を直す / 仕様を直す」で判断するときは必ずAskUserQuestionで確認
