# /test

仕様からテストケースを導出するスキル。
対象プロジェクトのテストランナー、テスト配置、ヘルパー構成を読み、不足しているテスト軸を補完する。

## トリガー条件

- 「{機能名}のテスト範囲を広げて」、「失敗する条件と値の上下限を網羅して」
- TDDサイクルや実装が終わったあと
- リファクタ前に安全網を広げたいとき
- バグ修正後に同じパターンの抜けを確認したいとき

## 入力

- `constitution.md`
- 対象の `spec/*.md`（1 つでも複数でもよい）
- 既存テストファイル
- 対象実装ファイル
- テスト実行コマンド
- テストランナー設定（`vitest.config.ts` / `jest.config.js` / `pytest.ini` 等の `include` / `testMatch` / `testpaths`）

## 出力

既存テストファイルまたは新規テストファイルに、以下4軸の不足分を追加する。

- 正常系
- 異常系
- 境界条件
- 状態遷移

合わせて、必要なテストヘルパーがあれば対象プロジェクトの既存規約に合わせて切り出す。

最後に以下のサマリーを出力する。

```markdown
# /test実行サマリー

対象機能: {機能名}
対象spec: spec/{機能ID}_{機能名}.md
対象テスト: {テストファイルパス}

## 追加件数

| 軸 | 既存 | 追加 | 合計 | 判定 |
|---|---|---|---|---|
| 正常系 | {n} | {n} | {n} | {実行済み / 検証不能と理由} |
| 異常系 | {n} | {n} | {n} | {実行済み / 検証不能と理由} |
| 境界条件 | {n} | {n} | {n} | {実行済み / 検証不能と理由} |
| 状態遷移 | {n} | {n} | {n} | {実行済み / 検証不能と理由} |

## テスト実行結果

{PASS / FAILの内訳}
```

## 作業手順

1. 入力ファイル確認
   `constitution.md`、対象 spec、既存テスト、対象実装を読み込む。対象 spec が複数ある場合は spec ごとに実装の有無を確認する。

2. テスト配置先の決定
   テストランナー設定の `include` / `testMatch` を読み、**そのランナーが実際に拾うディレクトリ**にテストを置く。設定を読まずに実装ファイルの隣（コロケーション）へ置くと、`include` の対象外だった場合にテストが無言でスキップされ、実行時に `No test files found` になったり件数が 0 のまま気づけない。既存テストの実際の配置場所を優先する。

3. カバレッジ差分の洗い出し
   spec の受入条件・境界条件と既存テストを突き合わせ、4 軸のうち未カバーの観点だけを列挙する。既にカバー済みの軸に水増しは追加しない。

4. テスト追加と実行
   未カバー分を追加し、テストランナーで実行して PASS を確認する。追加したテストが既存の PASS を崩さないことも確認する。

5. サマリー出力
   下記サマリーを spec 単位で出力する。実装が存在しない spec は「実装なしのためテスト追加不可」と明記し、追加件数を0とする。実装は存在しても現ハーネスで観測できない軸は「検証不能」と理由を記載する。

## 4軸の判定基準

### 正常系

- 受入条件ごとの主経路
- 仕様に書かれた代替経路
- 権限や入力パターンが分かれる場合は、その分岐

### 異常系

- 入力エラー
- 権限エラー
- 整合性エラー
- 対象リソースが存在しないケース

### 境界条件

- 最小値、最大値
- 最大値の内側と外側
- 空、null、未指定
- 仕様に書かれた上限・下限

### 状態遷移

- 遷移前、操作、遷移後の観測
- 主要な作成・更新・削除・復元などの状態変化

## 注意事項

- テストランナーや記法をスキル内で固定しない
- テスト配置は必ずランナー設定（`include` / `testMatch`）に従う。設定外の場所に置くと無言でスキップされる
- 既存テストを上書きしない
- 対象 spec の実装が存在しない場合はテストを書けない。無理にテストを書かず「実装なし」として報告し、先に `/implement` か `/tdd` が必要な旨を示す
- 実装は存在するが、現在のテスト基盤では観測できない軸（例: 実 DB や認証モックが無く、Route Handler のステータスコードや副作用を exercise できない）は、無理に薄いテストで埋めず「実装あり・現ハーネスで検証不能」として区別して報告する。pure logic 層で観測できる軸を優先して埋める
- 仕様と実装が食い違う場合は、どちらを直すかユーザーに確認する
