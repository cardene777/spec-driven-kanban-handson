# /design

仕様を実装へ移すための設計を作るスキル。
`spec/*.md` に書かれた要件と `constitution.md` の使用技術、性能・運用の目標、ロールごとの操作可否を読み、対象プロジェクトに合わせた設計へ落とし込む。

## トリガー条件

- 「この仕様の設計を書いて」、「このspecを設計に落として」
- `spec/*.md` ができたあと、実装の前に呼ぶ

## 入力

- `constitution.md`
- 対象の `spec/*.md`
- 既存の `design/*.md`
- 既存コードやディレクトリ構成（必要な場合）

## 出力

`design/{機能ID}_{機能名}.md` を生成する。

```markdown
# {機能名}の設計

## 関連仕様

## 前提

- {共有部品・依存 design・既存確定事項の参照。未実装フィールドに依存する場合はここで「新規追加 (要 migration)」と明示}

## データモデル

## API設計

## UI構造

{領域構成と状態の所在まで。部品分類・色・階層は `/ui-design` (`_ui.md`) と `/design-system` に委ねる}

## 状態遷移

- {エンティティ状態 / UI 状態の遷移。無ければ「なし」}

## 非機能の実装方針

### 性能

- {constitution.mdとspecに基づく実装方針}

### セキュリティ

- {constitution.mdとspecに基づく実装方針}

### 運用

- {constitution.mdとspecに基づく実装方針}

## 権限チェックの配置

| 対象 | チェック内容 | 失敗時 |
|---|---|---|
| {APIまたは処理} | {必要な権限} | {エラー応答} |

## 監査ログ

| 操作 | ログレベル | 記録する項目 |
|---|---|---|
| {操作} | {レベル} | {項目} |

## 実装方針

- {実装に入る前に固定する判断。相反する 2 案を両方残さず採用案 1 つに集約し、退けた案は理由 1 文で併記}

## テスト方針

- {テスト構成・ケース一覧・補助ヘルパの方針}

## 実装順序

1. **{最初に作る共通部品}**

   {理由と依存関係}
2. **{次に作るAPIまたはモデル}**

   {理由と依存関係}
3. **{最後に接続する画面またはテスト}**

   {理由と依存関係}
```

## 作業手順

1. **入力ファイル確認**

   `constitution.md` と対象の `spec/*.md` を読む。
2. **既存設計・実スキーマ確認**

   既存 `design/` と実データモデル (schema 等) を読む。
   複数機能が共有するエンティティ (例 Card) のフィールド前提が先行設計・実スキーマと食い違う場合、本設計で勝手に別方式へ分岐せず、先行設計側の是正要否を明記する (単一 field ↔ 中間テーブル等、方式が二分するときはどちらを正とするか 1 箇所に固定する)。
   まだ存在しないフィールドに依存する場合は「存在する前提」と書かず「本設計で新規追加 (未実装のため要 migration)」と区別して書く。
3. **基本設計作成**

   対象仕様からデータモデル、API、UI構造を起こす。
4. **横断要件の設計**

   非機能の実装方針、権限チェックの配置、監査ログ、実装方針を書く。
5. **技術選択の明示**

   技術選択は `constitution.md` の技術スタック範囲内で行う。
   ORM/DB 固有機能 (Prisma の `mode` / `fullTextSearch` / DB 関数 / 照合順序 等) を設計に書く場合、`constitution.md` で宣言された provider がその機能を実際に対応するか確認する。未対応なら代替 (例 SQLite では大文字小文字非依存検索を保存時正規化列や `LOWER()` で代替) を設計側に明記し、対応保証のない機能を「固定する判断」に含めない。
6. **実装順序の整理**

   依存関係、先に作る共通部品、後から接続する画面、テストの順番を明記する。
7. **ファイル書き出し**

   ユーザー承認後にファイルを書き出す。

## 注意事項

- 仕様にない要件を勝手に追加しない。仕様変更が必要なら `/spec` に戻る
- 認証方式、権限名、フレームワーク、テストランナーは `constitution.md` から読む
- スキル内に特定プロジェクトのAPIパス、モデル名、ロール名を固定しない
- 他機能で確定済みのデータモデル方式 (単一 field か中間テーブルか等) と矛盾する設計を単独で確定しない。矛盾を見つけたら該当 design の是正を併記する
- 「実装方針」の固定判断は、同一文書内の他判断・データモデル・API 設計と矛盾しないこと、かつその判断の消費者 (そのレスポンス項目を使う UI/機能) が本設計内で示せることを確認する
- `UI構造` は領域構成と状態の所在までに留め、部品分類・色・階層は `/ui-design` (`_ui.md`) と `/design-system` に委ねる。特定の component 分類法を本設計で確定しない
- 後続機能で先行設計の前提を変える場合は `## 既存設計との差分` セクションを追加する
