# /document

仕様・コード・テストからドキュメントを自動生成するスキル。
APIリファレンス・ユーザーヘルプ・運用runbookの3種類を1度のスキル呼び出しで生成する。

## トリガー条件

- 「{機能名} のドキュメントを生成して」、「API仕様書を書いて」、「runbookを更新して」
- 本章用の`/implement`で実装が完了し `/review` で0件判定が出たあと
- 仕様変更があったあとのドキュメント追従
- CIワークフローからの自動呼び出し

## 引数

- `--type api` APIリファレンスのみ生成
- `--type help` ユーザーヘルプのみ生成
- `--type runbook` 運用runbookのみ生成
- `--type all` 3種類すべて生成（省略時は標準）
- `--all` 対象機能を指定せず、変更検知された全機能を生成

## 入力

- `constitution.md`（用語集・権限ポリシー参照用）
- 対象の`spec/*.md`（FR・非機能・権限・用語の元）
- 対象の`design/*.md`（APIパス・データモデルの元）
- 対象実装ファイル一式（route.ts・page.tsx・コンポーネント）
- 対象テストファイル一式（テストケースからFAQを派生）
- `.github/workflows/`（runbook生成時のCI連動情報）
- `.env.*.example`（runbook生成時の環境変数情報）

## 出力

引数 `--type` に応じて以下を生成する。

| 引数 | 出力先 | 想定読者 |
|---|---|---|
| `api` | `docs/api/{機能ID}_{機能名}.md` | フロントエンド開発者・APIクライアント |
| `help` | `docs/help/{機能ID}_{機能名}.md` | エンドユーザー・サポート担当 |
| `runbook` | `docs/runbook/{機能ID}_{機能名}.md` | SRE・運用担当 |

## 作業手順

1. 仕様と設計確認
   `constitution.md` と対象 `spec/*.md` `design/*.md` を読み込む。
2. 実装確認
   対象実装ファイル一式をGlob + Readで読み込む。
3. テスト確認
   対象テストファイル一式をGlobで抽出し、テストケース名と件数を集計する。
4. ドキュメント生成
   `--type` に応じて1〜3種類のドキュメントを生成する。
5. ファイル書き出し
   各ドキュメントを対応する `docs/{種別}/` に書き出す。
6. 矛盾の記録
   4ファイル（仕様 / 設計 / 実装 / テスト）間で矛盾が見つかったらレポート末尾に警告として記載する。
7. サマリー返却
   生成完了サマリーを返す。

### --type apiの追加手順

- APIハンドラ（`route.ts` のexport関数）を抽出
- リクエストボディのzodスキーマやJSON構造を読み取り、フィールド表を生成
- レスポンスのステータスコード分岐をGrepで抽出し、レスポンス表を生成
- テストファイルを参照し「関連テスト」セクションを生成

### --type helpの追加手順

- ページコンポーネント（`page.tsx`）から画面操作の流れを抽出
- 仕様の異常系（422 / 409 / 401）からFAQ質問を派生
- 技術用語（status code / JWT / bcrypt）を平易な表現に置き換える
- スクリーンショットの参照は `docs/help/images/` をGlobで確認

### --type runbookの追加手順

- 実装ファイルから `logger.error` / `logger.warn` の出力箇所をGrep
- `lib/metrics.ts` 経由のメトリクス送信箇所をGrep
- `.env.*.example` の環境変数を確認し関連変数を抽出
- `.github/workflows/` から関連CIワークフローを参照
- 障害シナリオは「ログ + メトリクス + 依存先」の組み合わせから2〜3件生成

## CI組み込みの推奨設定

GitHub Actionsで `paths` フィルタを設定し、関連ファイル変更時のみ走らせる。

```yaml
on:
  push:
    branches: [main]
    paths:
      - 'spec/**'
      - 'app/api/**'
      - 'app/**/page.tsx'
      - '__tests__/**'
```

生成結果はPRとして作り、人手レビューを1段挟む。

| 運用パターン | メリット | デメリット |
|---|---|---|
| 手動 `/document` | レビュー負荷小 | 更新忘れ |
| CI自動 + PRレビュー (推奨) | 更新漏れゼロ | PRが増える |
| CI自動 + 自動マージ | 最も省力 | 誤生成リスク |

## 注意事項

- ドキュメントを直接編集せず、必ず仕様・コード変更を経由して再生成する（SSOT化）
- 生成済みドキュメントをReadしてから上書きする（既存の手動追記があれば警告）
- 技術用語と平易表現の使い分けは `--type` ごとに切り替える（helpは平易、api / runbookは技術用語可）
- 「適切に」、「いい感じに」のような曖昧表現を生成しない
- 4ファイル間矛盾は警告として残し、ユーザーの判断を仰ぐ（独断で仕様 / コードを書き換えない）
- runbookの障害シナリオは実装に存在するログ・メトリクスから抽出する（架空のシナリオを作らない）
