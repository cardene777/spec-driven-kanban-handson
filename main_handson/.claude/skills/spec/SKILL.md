# /spec

ユーザーから渡された要望を、実装前に確認できる仕様へ変換するスキル。
`constitution.md` の使用技術、性能・運用の目標、ロールごとの操作可否、用語を参照し、対象機能に必要な仕様だけを構造化する。

## トリガー条件

- 「{機能名}の仕様を書いて」、「この要望をspecにして」
- 新機能を実装する前に、操作、失敗条件、運用上の制約、ロールごとの操作可否を整理する場合

## 入力

- `constitution.md`
- 機能の自然言語要望
- 関連する既存仕様

## 出力

`spec/{3桁ゼロ埋め連番}_{英語スネークケース機能名}.md` を生成する（例 `006_label.md` / `007_due_date.md` / `009_assignee.md`）。
機能名は `constitution.md § 用語集` の英訳をスネークケース化し（Label→label、Due Date→due_date）、連番は既存 `spec/` の最大番号 +1 とする。日本語ファイル名や桁数の揺れは作らない。
レビューレポートは `review/` 配下に置かれる（`/spec-review` の出力）ため、`spec/` の採番対象には含まれない。

以下の章構成で出力する。並び順もこのとおりにする。

```markdown
# {機能名}の仕様

## 概要

## 既存仕様との関係

## 対象データ

{エンティティと field を型つきで列挙。中間テーブルがあれば併記}

## 機能要件

### 操作: {操作名}

## 画面

{UI を伴う機能のみ。画面上の要素と操作を記述}

## API

| メソッド | パス | 用途 | 必要権限 |
|---|---|---|---|
| {GET/POST/...} | {/api/...} | {用途} | {対象リソースの権限} |

## 受入条件

- [ ] {YES/NO で検証可能な操作と期待結果を 1 行 1 条件で。ステータスコード・エラーコードを含める}

## 異常系

## 境界条件

## バリデーション

## 権限境界

| 操作 | 必要権限 | 異常時の動作 |
|---|---|---|
| {操作} | {constitution.mdで定義された権限} | {ステータスや画面表示} |

## 非機能要件

- {constitution.mdの該当項目を参照した要件}

## 使用する用語

- {用語}（constitution.md § 用語集 参照）

## 参照する既存ファイル

- constitution.md
- spec/000_shared_rules.md
- inputs/{該当}_spec_input.md（要望入力ファイルがある場合）
- 関連する既存 spec

## 未決事項

- {この spec で確定できず、後続で決める項目。無ければ「なし」}
```

## 作業手順

1. Constitution確認
   `constitution.md` をReadで読み込む。必要な項目がなければユーザーに通知する。
2. 要望の整理
   ユーザーの要望から対象機能、操作、入力、出力、制約を抽出する。
3. 既存spec確認
   関連する既存 `spec/` を読み込む。
4. 共通ルールの切り出し
   HTTP ステータス、認証・存在・権限・バリデーションの入口チェック順序、権限マトリクス、一覧レスポンス構造など複数機能で共通する規約は `spec/000_shared_rules.md` に集約し、各機能 spec からは再掲せず参照する。既に `spec/000_shared_rules.md` があれば新規機能はそれを参照する。
5. 基本仕様の作成
   対象データ（エンティティと型）、機能要件、API エンドポイント表、受入条件、成功条件、失敗条件、値の上下限、入力検証を書く。
6. 横断要件の反映
   性能・運用の目標、ロールごとの操作可否、用語参照を `constitution.md` に基づいて追記する。
7. 未登録用語の確認
   用語集にない用語が登場した場合、`/constitution` に追記するか確認する。
8. ファイル書き出し
   ユーザー承認後にファイルを書き出す。

## 注意事項

- 「適切な権限」、「セキュアに」などの抽象表現は禁止。具体的な条件を書く
- ロール名、権限名、ステータスコード、用語はスキル側で固定せず `constitution.md` とユーザー入力から決める
- 非機能要件は `constitution.md` の値を参照し、未定義ならユーザーに確認する
- 受入条件は YES/NO で検証可能な 1 行 1 条件にする。抽象表現で終わらせない
- 一覧レスポンスは `{ items: [...] }` 形状、入口チェック順序など複数 spec 共通の規約は `spec/000_shared_rules.md` を参照し各 spec で再定義しない
- 機能要件の項目は `### 操作: {操作名}` 形式で統一する。ID を付す場合は `FR-001` の 3 桁ゼロ埋めに固定し 2 桁と混在させない
