# /review

仕様・設計とコードを観点ごとに突合するスキル。
`constitution.md`、仕様、設計、実装を読み、基本5観点でずれの候補を深刻度付きのレビューレポートにまとめる。指摘の採否は人が判断する。
プロジェクトにデザインシステム（`brand.json` / デザイントークン / 共通レイアウト）が導入されている場合は、後述の一貫性観点を追加する。

## トリガー条件

- 「{機能名}のコードと仕様を突合して」、「仕様準拠か確認して」
- 実装が完了した直後
- 仕様変更があったあと
- 大規模リファクタの直後
- PRマージ前の最終確認

## 入力

- `constitution.md`
- 対象の `spec/*.md`
- 対象の `design/*.md`
- 対象実装ファイル一式
- 既存のレビューレポート
- デザインシステム導入時は `brand.json` / `app/tokens.css` / `components.json` / `components/ui/` / 共通レイアウト（`AppShell` 等）

## 出力

`review/{機能ID}_{機能名}_review.md` を生成する。

```markdown
# {機能名} レビューレポート

レビュー日時: {日時}
対象実装: {ファイルパス群}
対象仕様: spec/{機能ID}_{機能名}.md
対象設計: design/{機能ID}_{機能名}.md

## サマリー

| 観点 | Critical | Important | Polish |
|---|---|---|---|
| 仕様カバレッジ | {n} | {n} | {n} |
| 実装カバレッジ | {n} | {n} | {n} |
| 振る舞いの整合 | {n} | {n} | {n} |
| 権限境界の整合 | {n} | {n} | {n} |
| 用語の整合 | {n} | {n} | {n} |
| （デザインシステム導入時）一貫性観点 | {n} | {n} | {n} |

## 判定

- ある観点が0件でも他観点に不一致が出るのは正常。観点ごとに件数が混在する
- 全観点0件は達成状態というより、観点設計が対象に届いていない signal を疑う
- 各不一致に深刻度（Critical / Important / Polish）を付け、Critical から順に対応する
```

## 深刻度の3段階

- Critical: 動作しない / 仕様に反する / 権限やセキュリティの穴 / 読者が手順どおり進めて詰まる
- Important: 動作するが一貫性が壊れている（デザインシステムの適用漏れ、API とドキュメントの不一致など）
- Polish: 好みや将来改善の範囲

テストが全て PASS していても仕様との一致は別問題である。Critical はテストが緑のまま見逃されることがある。

## 5観点の判定基準

### 観点1: 仕様カバレッジ

仕様にあるがコードに無い可能性がある機能を確認する。

### 観点2: 実装カバレッジ

コードにあるが仕様に無い可能性がある処理を確認する。

### 観点3: 振る舞いの整合

仕様の入出力、ステータス、レスポンス、表示、状態変化と実装のずれを確認する。

### 観点4: 権限境界の整合

`constitution.md` と仕様に書かれた権限境界が実装されているか確認する。

### 観点5: 用語の整合

`constitution.md` の用語集と、仕様・設計・コード命名のずれを確認する。

## デザインシステム導入時の追加観点

プロジェクトに `brand.json` やデザイントークン、共通レイアウトがある場合、基本5観点に以下を足す。無い場合は追加しない。

### 観点6: デザイントークン一貫

色・書体・角丸が、hex 直書きや素の色クラスではなく、トークン参照（`var(--brand-*)` / semantic class）で書かれているかを確認する。

### 観点7: コンポーネント使用一貫

素の `<button>` / `<input>` / `<textarea>` / `<table>` が残っていないか、同じ役割に別実装が混在していないかを確認する。design-system で例外として残した native `<select>` は、token 由来の class が適用されているかを確認する。

### 観点8: 共通レイアウト適用一貫

共通レイアウト（`AppShell` 等）で包むべき画面が包まれているか、包まないと決めた画面（認証系など）が別ルールで統一されているかを確認する。

## 作業手順

1. 入力ファイル確認
   `constitution.md` と対象仕様・設計を読み込む。
2. 実装ファイル確認
   対象実装ファイルを読み込む。
3. 前回レビュー確認
   既存レビューレポートがあれば確認する。
4. 観点の確定
   基本5観点を使い、デザインシステムがあれば観点6〜8を足す。
5. 不一致列挙
   各観点で不一致を列挙し、1件ごとに深刻度（Critical / Important / Polish）を付ける。
6. レポート生成
   深刻度付きのレビューレポートを生成する。
7. 修正方針確認
   修正が必要な場合、ユーザーに方針を確認する。Critical から順に対応する。

## 注意事項

- ロール名、用語、権限チェック関数名をスキル内で固定しない
- 仕様と実装のどちらを直すべきか判断できない場合はユーザーに確認する
- 自動修正前に、修正対象と理由を提示する
