# /review

仕様・設計とコードを機械的に突合するスキル。
仕様カバレッジ・実装カバレッジ・振る舞いの整合・権限境界の整合・用語の整合の5観点でずれを検出し、修正提案付きのレビューレポートを返す。

## トリガー条件

- 「{機能名} のコードと仕様を突合して」、「仕様準拠か確認して」
- 本章用の`/implement`でコードを生成した直後
- 仕様変更があったあと（既存コードが新仕様にどこまで追従できているかを確認）
- 大規模リファクタの直後（仕様準拠を保てたかを確認）
- PRマージ前の最終ゲート

## 入力

- `constitution.md`（権限ポリシー・用語集・非機能要件の参照用）
- 対象の`spec/*.md`（突合元の仕様）
- 対象の`design/*.md`（突合元の設計）
- 対象実装ファイル一式（APIハンドラ・コンポーネント・マイグレーション）
- 既存の `review/*_review.md`（前回レビューとの差分確認用）

## 出力

`review/{機能ID}_{機能名}_review.md` を生成する。
構成は以下のとおり。

```markdown
# {機能名} レビューレポート

レビュー日時: {日時}
対象実装: {ファイルパス群}
対象仕様: spec/{機能ID}_{機能名}.md
対象設計: design/{機能ID}_{機能名}.md

## サマリー

| 観点 | 不一致件数 |
|---|---|
| 仕様カバレッジ | {n} |
| 実装カバレッジ | {n} |
| 振る舞いの整合 | {n} |
| 権限境界の整合 | {n} |
| 用語の整合 | {n} |
| 合計 | {n} |

## 観点1: 仕様カバレッジ

| # | 仕様 | 実装の状態 | 修正案 |
|---|------|-----------|-------|

## 観点2: 実装カバレッジ

| # | 実装 | 仕様の状態 | 修正案 |
|---|------|-----------|-------|

## 観点3: 振る舞いの整合

| # | 仕様 | 実装 | 修正案 |
|---|------|------|-------|

## 観点4: 権限境界の整合

| # | 仕様 | 実装 | 修正案 |
|---|------|------|-------|

## 観点5: 用語の整合

| # | 仕様用語 | コード命名 | 修正案 |
|---|----------|-----------|-------|

## 判定

- 合計0件: マージ可能
- 合計1件以上: 修正必要（修正後に再度 /review）
```

## 5観点の判定基準

各観点で何を「不一致」と判定するかを以下にまとめる。

### 観点1: 仕様カバレッジ

仕様にあるがコードに無い機能を検出する。
- FR-XXXに対応するAPIハンドラが存在するか
- 非機能要件（タイムアウト・サニタイズ・キャッシュ）が実装されているか
- 異常系（401 / 403 / 404 / 409 / 422）の分岐が実装されているか

### 観点2: 実装カバレッジ

コードにあるが仕様に無い処理を検出する。
- 仕様外のAPIエンドポイントが追加されていないか
- 仕様に書かれていない副作用（外部API呼び出し・ログ送信）が混入していないか
- デバッグ用コード（console.log・任意の認証バイパス）が残っていないか

### 観点3: 振る舞いの整合

仕様の入出力とコードの返り値のずれを検出する。
- ステータスコードのマッピング（仕様422 vs実装400）
- レスポンスボディの構造（フィールド名・型）
- ソート順・ページングの有無
- バリデーションの上下限値

### 観点4: 権限境界の整合

権限ポリシーとコードの認可ロジックの整合を検出する。
- 仕様の権限表（owner / member / viewer × 操作）と実装の `requireRole` の対応
- 「投稿者本人」、「ボードメンバー」のような条件が実装されているか
- 認可漏れ（GETハンドラに権限チェックが無い等）の検出

### 観点5: 用語の整合

用語集とコードの命名のずれを検出する。
- 仕様用語（投稿者 / 担当者 / コメント）とDBカラム名・TypeScriptフィールド名の対応
- 表記揺れ（comment_text vs body、authorId vs userId）の検出
- 英訳のずれ（仕様の英語名と関数名）

## 作業手順

1. 入力ファイル確認
   `constitution.md` と対象 `spec/*.md` `design/*.md` を読み込む。
2. 実装ファイル確認
   対象実装ファイル一式をGlobで抽出し、Readで順に読み込む。
3. 前回レビュー確認
   既存の `review/{機能ID}_{機能名}_review.md` をGlobで探し、前回の不一致を把握する。
4. 不一致列挙
   5観点ごとに不一致を列挙する。
   - 仕様の各FR・非機能・権限・用語に対応するコード片を逆引きで探す
   - コードの各関数・分岐に対応する仕様記述を逆引きで探す
5. 修正案生成
   各不一致に対して具体的な修正案（ファイル名 + 行番号 + 変更前後）を生成する。
6. レポート生成
   出力テンプレートに従って `review/{機能ID}_{機能名}_review.md` を生成する。
7. 修正方針確認
   AskUserQuestionで「採用 / 不採用 / 別案」を1件ずつ確認する。
8. 修正反映
   採用された修正をファイルに反映する。
9. 再レビュー
   全件処理後、再度 `/review` を回し合計0件を確認する。合計0件をマージ可能判定とする。

## 修正承認の対話パターン

AskUserQuestionは1件ずつ以下の3択を出す。

| 選択肢 | 意味 | 動作 |
|---|---|---|
| A. 採用（推奨） | 修正案の通りに変更 | 対応ファイルを更新 |
| B. 不採用 | 仕様側を変更 | 仕様ファイルを更新（理由を記録） |
| C. 別案で進めたい | 第3の方針を採用 | 別案をAskUserQuestionで受け取り反映 |

`B. 不採用` を選んだ場合、レビューレポートに「{観点}-{番号}: 仕様変更を採用（理由: {ユーザー入力}）」を追記する。

## 注意事項

- レビューレポートを書く前に元のコード・仕様を勝手に書き換えない（必ずレポート → 承認 → 修正の2段階）
- 同一の不一致を複数観点に重複登録しない（最も適切な観点1つに集約する）
- 修正案は具体的に書く（「適切に修正」、「いい感じに対応」のような抽象表現は禁止）
- 用語整合の修正はDBマイグレーションを伴う場合があるので必ず明記する
- `B. 不採用` を選んでも仕様レビュー（`/spec-review`）には自動で回さない（独立した判断）
- 全件処理後、必ず再度 `/review` を回し合計0件 (マージ可能)を確認する
