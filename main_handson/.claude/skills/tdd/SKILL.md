# /tdd

Red-Green-Refactorのサイクルを自動運転するスキル。
本章用の`/spec`と`/design`で書かれた仕様と設計を入力として、受入条件を1件ずつRed → Green → Refactorの3フェーズで実装する。

## トリガー条件

- 「{機能名} をTDDで実装して」、「Red-Green-Refactorで進めて」
- 本章用の`/design`で設計が固まったあと、`/test-runner`の前
- バグ修正で「再現テストから始めたい」とき

## 入力

- `constitution.md`（技術スタック・規約参照用）
- 対象の`spec/*.md`（受入条件ACのリスト）
- 対象の`design/*.md`（実装方針）
- `design/*_ui.md`（UIコンポーネントが絡む場合）
- 既存テストファイル（命名規則・配置パスの参照用）

## 出力

各ACごとに以下を出力する。

| ファイル | 内容 | フェーズ |
|---|---|---|
| `{対象}.test.ts` | 失敗テスト | Red |
| `{対象}.ts` | 最小実装 | Green |
| `{対象}.ts` / `{対象}.test.ts` の更新 | リファクタ後の構造 | Refactor |
| `.context/tdd/cycles.md` | 各サイクルの記録（開始時刻・終了時刻・結果） | 全フェーズ |

サイクル全体が終わると、最後に以下のレポートを出力する。

```markdown
# TDDサイクルレポート

対象機能: {機能名}
対象spec: spec/{機能ID}_{機能名}.md
対象design: design/{機能ID}_{機能名}.md

## サマリー

| AC | Red | Green | Refactor | 結果 |
|---|---|---|---|---|
| FR-001 | FAIL確認済み | PASS | PASS維持 | 完了 |
| FR-002 | ... | ... | ... | ... |

## 検出した改善ポイント

- Greenフェーズが大きすぎるAC: {AC ID}（推奨: 仕様分割）
- Refactorで発覚した設計負債: {内容}
- 次回サイクルで気をつけること: {内容}

## 生成・更新したファイル

- {テストファイル一覧}
- {実装ファイル一覧}
```

## テスト実行コマンド

本書はNext.js + Vitestを前提とする。テストフレームワークに応じて以下を読み替える。

| フレームワーク | テスト実行コマンド |
|---|---|
| Vitest | `npm run test -- {ファイルパス}` |
| Jest | `npm test -- {ファイルパス}` |
| Playwright | `npx playwright test {ファイルパス}` |

スキル本文中の「テスト実行」は、上記コマンドのいずれかに置き換える。

## 作業手順

### 全AC共通の準備

1. 入力ファイル確認
   `constitution.md` と対象 `spec/*.md` `design/*.md` を読み込む。
2. AC抽出
   受入条件 (AC)を一覧で抽出し、AskUserQuestionで実装順序をユーザーに確認する。
3. サイクル記録開始
   `.context/tdd/cycles.md` を作成し、サイクル記録を開始する。

### Redフェーズ

1. テストファイル決定
   既存命名規則をGlobで参照し、対象ACのテストファイルパスを決定する。
2. テストコード作成
   テストコードを書く。1 ACにつき1〜数件とし、複数ACを同時に書かない。
3. FAIL確認
   テストを実行してFAILを確認する。
4. FAIL理由確認
   FAILの理由が想定通り（対象モジュールが無い、振る舞いが未実装）であることを確認する。
5. Green移行確認
   AskUserQuestionでGreenフェーズに進む承認を得る。

### Greenフェーズ

1. 最小実装
   対象ACを通す**最小限**の実装を書く。仕様外の処理を含めない。
2. 仮実装の利用
   必要に応じてin-memory実装やハードコード値で進める。本格実装はRefactorで行う。
3. PASS確認
   テストを実行してPASSを確認する。
4. リグレッション確認
   他の既存テストも実行し、リグレッションがないことを確認する。
5. Refactor移行確認
   AskUserQuestionでRefactorフェーズに進む承認を得る。

### Refactorフェーズ

1. 改善項目洗い出し
   重複・命名・責務の観点で整える項目を洗い出す。
2. 小さな変更
   1ステップごとに変更し、テストを再実行してPASSを保つ。
3. 本実装への置換
   仮実装（in-memory・ハードコード値）を本実装（DBアクセス・認証）に置き換える。
4. FAIL時確認
   もしテストがFAILしたら、その時点で停止しAskUserQuestionで方針を確認する。
5. 次AC移行確認
   AskUserQuestionで次のACに進む承認を得る。

### 全AC完了後

1. 全テスト確認
   全テストを実行し、すべてPASSしていることを確認する。
2. レポート生成
   `.context/tdd/cycles.md` をもとにTDDサイクルレポートを生成する。
3. 改善ポイント提示
   検出した改善ポイントをユーザーに提示する。

## 軌道修正の判断ポイント

スキルは以下の兆候を検出したらAskUserQuestionで軌道修正の判断をユーザーに渡す。

| 兆候 | 推奨される対応 |
|---|---|
| 1サイクル10分超過 | ACの分割（`/spec-review` に戻る） |
| Greenフェーズで実装が50行超 | 設計の見直し（`/design` に戻る） |
| Refactor中に新たなACが見つかる | 別サイクルとして切り出し |
| Refactor後にテストが連続でFAIL | 直前ステップに戻して別方針 |

## 注意事項

- Redフェーズで複数ACのテストをまとめて書かない（1 AC = 1サイクル）
- Greenフェーズで仕様外の実装を盛らない（テストが要求していないコードを書かない）
- Refactorフェーズでは振る舞いを変えない（テスト結果を変えてはいけない）
- 各フェーズの境界では必ずAskUserQuestionで承認を得る（無断で次フェーズに進まない）
- テスト実行は専用ツール（Bash）で行い、結果を必ず本文に貼り付ける
- `.context/tdd/cycles.md` は中間ファイルなのでgitにはコミットしない（`.gitignore` に追加）
