# /tdd

テスト先行 (Red) を担うスキル。
受入条件ごとに、まだ実装が無いために失敗するテストを書き、FAIL を確認するところまでを行う。
実装コードは書かない。テストを通す実装 (Green) とリファクタ (Refactor) は `/implement` に渡す。これにより「実装コードを書くのは `/implement` だけ」に一本化し、テスト先行と実装の責務を分ける。

## トリガー条件

- 「{機能名}をテスト先行で進めて」、「先に失敗するテストを書いて」
- 設計が固まったあと、実装に入る前
- バグ修正で再現テストから始めたいとき

## 入力

- `constitution.md`
- 対象の `spec/*.md`
- 対象の `design/*.md`
- UI設計文書（必要な場合）
- 既存テストファイルとテスト実行コマンド
- テストランナー設定（`vitest.config.ts`、`jest.config.*`など）

## 出力

- 失敗するテスト（受入条件ごと）
- `.context/tdd/cycles.md`（各受入条件の Red の記録と、`/implement` に渡す対象の一覧）

実装コードは出力しない。テストを通す実装は `/implement` が書く。

## テスト実行コマンド

テスト実行コマンドは、以下の優先順で決める。

1. `constitution.md` に明記されたコマンド
2. 既存の `package.json`、設定ファイル、CI定義にあるコマンド
3. 既存テストの実行方法
4. 不明な場合はユーザー確認

## 作業手順

### 準備

1. **入力ファイル確認**

   `constitution.md` と対象仕様・設計を読み込む。テスト配置はテストランナー設定（`vitest.config.ts` の `include` 等）が拾うディレクトリに合わせ、設定外の場所に置いて無言でスキップされるのを避ける。
2. **実装状況の確認**

   対象の受入条件が既に実装済みかを確認する。既に実装済みなら Red を作れないため、未実装の受入条件へスコープを移すか、ユーザーに方針を確認する。
3. **テスト単位の決定**

   1 テスト群 = 1 つの振る舞い単位。1 つの FR に細かい受入条件が複数ぶら下がる場合は、その FR をまとめて 1 群にしてよい。無関係な複数の振る舞いを 1 群に混ぜない。
4. **記録開始**

   `.context/tdd/cycles.md` を作成し、対象 FR と書いた失敗テストを記録する。

### Redフェーズ（このスキルの主担当）

1. **テストファイル決定**

   既存命名規則とテストランナー設定を参照し、対象受入条件のテストファイルパスを決める。
2. **テストコード作成**

   受入条件を満たすときだけ通るテストを書く。失敗理由は、未実装または期待する振る舞いとの差分でなければならない。設定不備、importパスの誤り、テスト環境の起動失敗によるFAILはRedとして扱わず、先に原因を報告する。
3. **FAIL確認**

   テストを実行し、期待どおり失敗することを確認する。失敗メッセージを記録する。

### 実装への引き継ぎ

1. **引き継ぎ**

   書いた失敗テストと対象受入条件を `/implement` に渡す。`/implement` がテストを通す最小実装（Green）と、テストを保ったままの整理（Refactor）を行う。
2. **Green確認**

   `/implement` 実行後、書いたテストが PASS することと、既存テストが壊れていないことを確認する。

## 注意事項

- `/tdd` は実装コードを書かない。テストを通す実装とリファクタは `/implement` が担う
- 無関係な複数の振る舞いを1つのテスト群に混ぜない（1つのFRに属する受入条件はまとめてよい）
- テストランナー、ファイルパス、テストスタイルをスキル内で固定しない
- テストはテストランナー設定が拾うディレクトリに置く（設定外に置くと実行されない）
- テストは受入条件の振る舞いを検証する。実装の内部構造に依存した、実装を書けば自動で通るだけのテストにしない
- DB、認証、外部サービスなどの前提が無く観測できない受入条件は、薄いモックで通過扱いにしない。必要なテスト基盤とともに「現ハーネスで検証不能」と記録する
