## 観点1: 曖昧表現

### 曖昧-1 [Middle] 「元リストのアクティブ集合の末尾に戻す」の元リストが消えている場合の挙動が未定義

- 問題箇所: spec/004 § 並び順の規則「アーカイブ復元／削除復元したカードは、元リストの**アクティブ集合の末尾**にアクティブとして戻す」
- 問題の理由: 復元対象カードの `listId` が指す List が、その後リスト削除（spec/002 の cascade）で失われている可能性がある。その場合の復元先が定義されていない。
- 修正案: 「復元時に `listId` の List が存在しない場合は 409/422 で復元不可とする」または「復元は List 存在を前提とし、List 削除時にカードの扱いを別途規定する（矛盾-2 と併せて確定）」のいずれかを明記する。
- 確認が必要な判断点: リスト削除とカード soft-delete/archive の相互作用（矛盾-2 参照）を先に決める必要がある。

### 曖昧-2 [Low] 冪等操作で `archivedAt` / `deletedAt` のタイムスタンプを更新するか未記載

- 問題箇所: spec/004 § 機能要件「再アーカイブは冪等（状態を変えず成功）」
- 問題の理由: 「状態を変えず」がフラグの有無を指すのか、タイムスタンプ値も不変かが曖昧。テスト時に `archivedAt` の値比較で揺れる。
- 修正案: 「再操作時は既存の `archivedAt`/`deletedAt` を変更しない（タイムスタンプも更新しない）」と明記。
- 確認が必要な判断点: なし（推奨どおりで問題なければ確定可能）。

## 観点2: 抜け漏れ

### 抜け漏れ-1 [High] 別リスト移動時、`targetListId` が同一ボードに属する制約がない

- 問題箇所: spec/004 § 操作: カードの移動（別リストへ）／§ バリデーション
- 問題の理由: `targetListId` が別ボードのリストでも受理し得る仕様になっており、カードが所属ボードを越えて移動できてしまう（権限・スコープの穴）。権限チェックも「どのボードの member か」が曖昧になる。
- 修正案: 「`targetListId` は対象カードの現在のボード（`sourceList.boardId`）と同一ボードに属すること。異なるボードは 422 / VALIDATION_ERROR（または 404）」をバリデーションと受入条件に追加する。
- 確認が必要な判断点: 別ボードへの移動を将来サポートするか（現状は禁止で確定してよいか）。

### 抜け漏れ-2 [High] リスト削除（spec/002 cascade）と soft-delete/archive 状態カードの相互作用が未定義

- 問題箇所: spec/004 § 対象データ（archivedAt/deletedAt 追加）と spec/002 § 操作: リスト削除「配下のカードも削除する」
- 問題の理由: spec/002 のリスト削除は配下カードを物理 cascade 削除する前提。soft-delete/archive 済みカードも一緒に物理削除されるのか、ゴミ箱に残すのかが未定義。復元（曖昧-1）とも直結する。
- 修正案: 「リスト削除時は、そのリストのカード（active/archived/deleted すべて）を物理 cascade 削除する」を明記し、リスト削除後は当該カードの復元不可であることを受入条件化する（実装の DB cascade と一致させる）。
- 確認が必要な判断点: リスト削除時に archived/deleted カードも巻き込んで物理削除してよいか（推奨: cascade 物理削除）。

### 抜け漏れ-3 [Middle] 完全削除（purge）の前提状態が未指定

- 問題箇所: spec/004 § 操作: カードの完全削除（purge）／§ API
- 問題の理由: purge が「deleted 状態（ゴミ箱内）のカードのみ」を対象とするのか、active/archived を含む任意のカードを owner が物理削除できるのかが未定義。
- 修正案: 「purge は `deletedAt != null`（ゴミ箱内）のカードのみ対象。active/archived への purge は 422 / VALIDATION_ERROR」または「owner は状態を問わず purge 可能」のいずれかに確定し、受入条件を追加。
- 確認が必要な判断点: purge をゴミ箱内限定にするか、任意状態を許すか。

### 抜け漏れ-4 [Middle] リスト並べ替えの `targetOrder` 範囲バリデーションが受入条件に落ちていない

- 問題箇所: spec/004 § 操作: リストの並べ替え／§ 受入条件
- 問題の理由: カードの `targetOrder` 範囲外は 422 の受入条件があるが、リスト move の範囲外（0未満・ボード内リスト数超過）の受入条件・境界条件が欠けている。
- 修正案: 「POST /api/lists/[listId]/move で `targetOrder` が 0 未満または（ボード内リスト数）超過は 422」を異常系・受入条件に追加。
- 確認が必要な判断点: なし。

### 抜け漏れ-5 [Middle] `archivedAt` と `deletedAt` が同時に設定され得るときの復元後の状態が未定義

- 問題箇所: spec/004 § 対象データ「アクティブ = archivedAt==null かつ deletedAt==null」／§ 各復元操作
- 問題の理由: アーカイブ済みカードをさらに soft-delete できる場合、削除復元（deletedAt を null）しても archivedAt が残り「末尾にアクティブとして戻す」と矛盾する（アクティブでない）。2フラグの独立性と復元の相互作用が未定義。
- 修正案: 次のいずれかに確定。(a) archive と delete は排他とし、archived カードは delete 不可（逆も同様）／(b) 2フラグは独立を許し、「復元/アーカイブ復元は自フラグのみ解除し、他フラグが残る場合はアクティブ集合に戻さず状態維持」と明記。
- 確認が必要な判断点: 2状態の排他 or 独立、および独立時の復元挙動。

### 抜け漏れ-6 [Low] `?status` に不正値を渡した場合の応答が未定義

- 問題箇所: spec/004 § API `GET .../cards?status=active|archived|deleted`
- 問題の理由: `status=foo` など未定義値のときの挙動（422 か active 既定にフォールバックか）が未記載。
- 修正案: 「未定義の `status` は 422 / VALIDATION_ERROR」または「未知値は既定 active にフォールバック」を明記。
- 確認が必要な判断点: 厳格（422）か寛容（フォールバック）か。

## 観点3: 矛盾

### 矛盾-1 [High] spec/003 の DELETE 定義（物理削除）と spec/004 の再定義（ソフト削除）が併存している

- 問題箇所: spec/003_cards.md § API「DELETE /api/cards/[cardId] … カード削除（物理）」 vs spec/004 § API「DELETE /api/cards/[cardId] … ソフト削除」
- 問題の理由: 同一エンドポイントの意味が2つの spec で食い違う。実装者がどちらに従うか分岐する。spec/004 § 既存仕様との関係「差分1」で認識済みだが、spec/003 本体は未修正のまま。
- 修正案: spec/003_cards.md の DELETE を「ソフト削除（spec/004 で再定義）」へ更新し、物理削除は `/purge`（owner）へ分離する旨を追記する。spec/004 を正とし spec/003 を追従させる。
- 確認が必要な判断点: spec/003 本体を今回のサイクルで更新するか、spec/004 の差分記述のみで実装を進めるか（実装前に一本化が必要）。

### 矛盾-2 [High] spec/003 の GET カード一覧（全件）と spec/004 の既定フィルタ（active のみ）が食い違う

- 問題箇所: spec/003_cards.md § 受入条件「GET /api/lists/[listId]/cards は items を order 昇順で返す（全件）」 vs spec/004 § 既存仕様との関係「差分2: 既定で active のみ」
- 問題の理由: 一覧の返却対象が2 spec で異なり、受入条件が衝突する。
- 修正案: spec/003_cards.md の GET を「既定は active のみ、`?status` で archived/deleted を取得」に更新し、spec/004 と一致させる。
- 確認が必要な判断点: 矛盾-1 と同じく spec/003 本体更新の是非・タイミング。

## 観点4: テスト不能項目

### テスト不能-1 [Middle] ドラッグ&ドロップ操作自体の受入条件が UI 挙動として観測条件化されていない

- 問題箇所: spec/004 § 画面「ドラッグ&ドロップ」
- 問題の理由: 「ドラッグして並べ替えできる」は自動テストで観測しにくい。API 受入条件（move）で代替される想定だが、その対応関係が明示されていない。
- 修正案: 「D&D の並べ替え結果は POST /api/cards/[cardId]/move（および list move）の受入条件で検証する。UI 層は当該 API 呼び出しの発火をもって満たすとみなす」と明記。
- 確認が必要な判断点: なし。

### テスト不能-2 [Low] 「アクティブ集合の末尾に戻す」の検証手段が受入条件に無い

- 問題箇所: spec/004 § 機能要件（復元操作）
- 問題の理由: 「末尾に戻る」ことは受入条件にあるが（restore/unarchive）、`order` が既存最大+1（=末尾）になる具体値の期待が明示されていない。
- 修正案: 受入条件を「復元後の対象カードの order = 復元先リストのアクティブ件数（末尾 index）」と数値化する。
- 確認が必要な判断点: なし。

## 全体総括

実装前に決めるべき High 論点は次の3点：

1. **spec/003 との一本化（矛盾-1・矛盾-2）**: DELETE のソフト削除化と GET の active 既定を spec/003 本体へ反映するか。実装が同一エンドポイントで分岐するため、実装前の一本化が必須。
2. **移動スコープの制約（抜け漏れ-1）**: 別リスト移動を同一ボード内に限定する制約を明文化（スコープ/権限の穴）。
3. **リスト削除 × soft-delete/archive の相互作用（抜け漏れ-2、関連: 曖昧-1・抜け漏れ-5）**: リスト削除時に archived/deleted カードも cascade 物理削除するか。復元先の存在保証にも直結。
