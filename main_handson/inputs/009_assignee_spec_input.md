# Assignee Spec Input

カードに担当者を割り当てる機能の仕様を書くための入力です。
TDDで使えるように、受入条件をFRごとに分けます。本節で実装・テストするのは、`userId`の入力検証と担当者数上限を判定する純粋関数の受入条件だけです。

## 読み込むファイル

- constitution.md
- spec/000_shared_rules.md
- spec/001_boards.md
- spec/002_lists.md
- spec/003_cards.md
- spec/005_card_detail.md

## 作成するファイル

- spec/009_assignee.md

## 対象

- カードに担当者を追加する
- カードから担当者を削除する
- カードの担当者一覧を取得する
- カード詳細に担当者を表示する

## 入力制約

- cardIdとuserIdは必須
- 1カードに設定できる担当者は最大10名
- 同じユーザーを2回追加した場合は409
- ボードメンバーではないユーザーを担当者にした場合は422
- すでに担当者であるユーザーを追加する場合は、人数上限より先に重複として409を返す

## 権限

- member以上は担当者を追加、削除できる
- viewerは担当者一覧を閲覧できる
- 未ログインは401
- 権限不足は403

## 境界条件

- 担当者0人
- 担当者10人
- 担当者10人のカードに11人目を追加する
- 存在しないカード
- 存在しないユーザー

## CHAPTER 05の第6節から第8節で実装・テスト・レビューする範囲

CHAPTER 05の第6節から第8節では、担当者の追加、削除、一覧取得、カード詳細表示のうち、外部依存を持たない以下の受入条件だけを純粋関数として実装・テスト・レビューします。

- `userId`が文字列であり、前後の空白を除いた後に1文字以上あることを検証する
- 担当者が9人のカードには追加を許可し、10人のカードには追加を拒否する

CHAPTER 05の第6節から第8節では、APIの409 / 422 / 401 / 403、カード・ユーザーの存在確認、ボードメンバー判定、DB更新、カード詳細UIを実装しません。純粋関数のテストが通っても、保存、API、認証、画面の動作は確認できません。

## 出力ルール

- 指定した1ファイルだけを作成または更新する
- 機能要件、受入条件、異常系、境界条件、バリデーション、権限境界、カード詳細画面での表示、未決事項を分けて書く
- TDDで扱えるように、各FRには観測可能な完了条件を含める
- 不明点がある場合は、仕様を書き始める前に質問する
- 完了時に、作成または更新したファイルを一覧で報告する
