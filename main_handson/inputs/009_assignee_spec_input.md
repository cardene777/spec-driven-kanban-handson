# Assignee Spec Input

カードに担当者を割り当てる機能の仕様を書くための入力です。
TDDで使えるように、受入条件をFRごとに分けます。この入力は担当者機能全体の完成イメージを記述するためのものであり、本章のTDDで一度に全てを実装する指示ではありません。

## 読み込むファイル

- constitution.md
- spec/000_shared_rules.md
- spec/001_boards.md
- spec/002_lists.md
- spec/003_cards.md
- spec/005_card_detail.md

## 作成するファイル

- spec/009_assignee.md

## 対象

- カードに担当者を追加する
- カードから担当者を削除する
- カードの担当者一覧を取得する
- カード詳細に担当者を表示する

## 入力制約

- cardIdとuserIdは必須
- 1カードに設定できる担当者は最大10名
- 同じユーザーを2回追加した場合は409
- ボードメンバーではないユーザーを担当者にした場合は422

## 権限

- member以上は担当者を追加、削除できる
- viewerは担当者一覧を閲覧できる
- 未ログインは401
- 権限不足は403

## 境界条件

- 担当者0人
- 担当者10人
- 担当者10人のカードに11人目を追加する
- 存在しないカード
- 存在しないユーザー

## 本章のTDDで実装・テストする範囲

セクション06〜08では、上の機能全体のうち、外部依存を持たない次の受入条件だけを純粋関数として実装・テスト・レビューします。

- `userId` が空でない文字列であることを検証する
- 現在の担当者数が9人なら追加を許可し、10人なら追加を拒否する

APIの409 / 422 / 401 / 403、カード・ユーザーの存在確認、ボードメンバー判定、DB更新、カード詳細UIは、実DBと認証モックを用意する統合実装の範囲です。これらはこの純粋関数のPASSだけで実装済みとは判断しません。

## 出力ルール

- 指定した1ファイルだけを作成または更新する
- 機能要件、受入条件、異常系、境界条件、バリデーション、権限境界、カード詳細画面での表示、未決事項を分けて書く
- TDDで扱えるように、各FRには観測可能な完了条件を含める
- 不明点がある場合は、仕様を書き始める前に質問する
- 作成または更新したファイル一覧を最後に示す
