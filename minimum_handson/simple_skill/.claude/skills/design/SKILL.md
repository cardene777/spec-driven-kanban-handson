# /design

仕様（spec.md）を入力として、実装に必要な技術的な設計を起こすスキル。
ここで決めるのは「何を作るか」ではなく「どう作るか」。

## トリガー条件

以下のいずれかに該当する場合に呼び出す。

- 「この仕様の設計を書いて」、「{機能名}の設計を起こして」
- spec.mdができたあと、implementの前に呼ぶ
- 既存設計を更新したいとき

## 入力

- `constitution.md`（プロジェクト方針）
- 対象の `spec/*.md`（1ファイルまたは複数ファイル）
- 既存の `design/*.md`（関連設計があれば）

## 出力

`design/{機能ID}_{機能名}.md` を生成する。
構成は以下のとおり。

```markdown
# {機能名}の設計

## 関連仕様

- spec/{該当ファイル}.md

## データモデル

### {エンティティ名}

| フィールド | 型 | 制約 |
|---|---|---|
| id | string | PK、cuid |
| {フィールド} | {型} | {制約} |

### リレーション

- {Entity1} は {Entity2} を1対多 で持つ

## API設計

| メソッド | パス | 概要 | 仕様 |
|---|---|---|---|
| GET | /api/{resource} | 一覧取得 | FR-001 |
| POST | /api/{resource} | 作成 | FR-002 |

### リクエスト・レスポンス例

#### POST /api/{resource}

リクエスト

\`\`\`json
{
  "title": "サンプル"
}
\`\`\`

レスポンス（200）

\`\`\`json
{
  "id": "abc123",
  "title": "サンプル"
}
\`\`\`

レスポンス（400）

\`\`\`json
{
  "error": "Validation Error",
  "details": { "title": "Required" }
}
\`\`\`

## UI構造

### ページ構成

| パス | 画面 | 関連機能 |
|---|---|---|
| / | ボード一覧 | FR-001 |

### コンポーネント階層

\`\`\`
PageBoardList
├── BoardCard
└── BoardCreateButton
\`\`\`

## 実装方針

- データアクセス層は `lib/repository/` に分離
- APIハンドラは `app/api/` のルートハンドラ
- 状態管理はReactのuseStateで十分（規模に応じて再検討）

## 参考

- constitution.md {該当する原則}
- spec/{該当ファイル}.md
```

## 作業手順

1. 入力ファイル確認
   `constitution.md` と対象 `spec/*.md` を読み込む。
2. 既存設計確認
   既存 `design/` をGlobで探し、関連があれば読み込む。
3. 設計要素の導出
   以下を仕様から導出する。
   - データモデル（テーブル定義、リレーション）
   - API設計（エンドポイント、リクエスト・レスポンス形式）
   - UI構造（ページ、コンポーネント階層）
   - 実装方針（ディレクトリ構成、依存ライブラリ）
4. 技術判断の確認
   仕様にない技術判断が必要な場合はAskUserQuestionで聞く。
5. design生成
   上記テンプレートに従って `design/{連番}_{機能名}.md` を生成する。
6. ファイル書き出し
   ユーザー承認後にファイルを書き出す。

## 注意事項

- 仕様に書かれていない要件を勝手に追加しない（仕様変更が必要なら `/spec` に戻す）
- 技術選定はconstitution.mdの範囲内で行う
- APIのステータスコードはspec.mdの異常系と必ず対応させる
- 1ファイル1機能、横断的な設計（認証、ロギング）は別ファイル
