# /implement

仕様と設計をコードに落とすスキル。
`constitution.md` の技術スタック・規約、`spec/*.md`、`design/*.md` を読み、対象プロジェクトの構成に合わせて実装する。
生成後は、報告した確認コマンドとブラウザ操作で、仕様どおりに動くかを確認する。

仕様と設計に書かれた範囲だけを実装する。仕様に含まれない機能を補完で追加しない。

## トリガー条件

以下のいずれかに該当する場合に呼び出す。

- 「この仕様を実装して」、「{機能名}のコードを書いて」
- `spec/*.md` と `design/*.md` が揃ったあと
- 仕様変更後の再生成

## 入力

- `constitution.md`（技術スタックと規約）
- 対象の `spec/*.md`
- 対応する `design/*.md`
- 既存コード（差分実装の場合）
- 既存のテスト・ビルド・lintコマンド

## 出力

仕様と設計に従って、必要なファイルを生成または更新する。技術スタックは `constitution.md` に従う。

- データモデルまたは永続化層
- APIやサーバー側処理
- UIまたは画面側処理
- 共通処理（エラーレスポンス、バリデーションなど）
- 対応するテスト（最低限）

各ファイルには、対応する仕様要件IDをコメントで残す（例 `// FR-001`）。

## 作業手順

1. 入力ファイル確認
   `constitution.md`、対象 `spec/*.md`、対応する `design/*.md` を読み込む。
2. プロジェクト初期化確認
   `package.json` や設定ファイルが無く、空のプロジェクトから作る場合は、`constitution.md` の技術スタックに従って初期化する。
   フレームワーク・ORM・テストランナーの初期化とセットアップは、そのスタックの標準的な手順に従う。手順が不明な場合や既存設定と衝突しそうな場合は、推測で進めず理由を報告する。
3. 既存コード確認
   Globで関連ファイルを探し、既存コードとディレクトリ構成、実行コマンドを把握する。
4. 不足ファイル生成
   不足ファイルを、design の実装順序に沿って生成する。
   - データモデル
   - バリデーション
   - データアクセス層
   - APIハンドラ
   - UIコンポーネント
   - テスト
5. 要件IDの記録
   各ファイル生成後、対応する仕様要件IDをコメントに残す。
6. 異常系実装
   異常系のレスポンスは `spec/*.md` の異常系表と `design/*.md` のAPI設計どおりに実装する。対象リソースが無い場合は先に404を返し、対象がある場合だけ入力を検証して400を返す。
7. 静的検証
   `constitution.md § 検証コマンド`（無ければ `package.json` や設定から判断）に従い、lint、typecheck、test、build を順に実行して通ることを確認する。実行できないコマンドは理由とともに未完了として報告する。
8. 失敗時対応
   失敗したら修正して再実行する。3回失敗したら止めてユーザーに報告する。

## コード生成の方針

- フレームワーク、ORM、テストランナーをスキル内で固定しない。`constitution.md` の技術スタックに従う
- 既存のプロジェクト構成と規約を優先する
- 仕様にない機能をついでに追加しない
- エラー処理は `constitution.md` と設計に従う（`{ "error": { "code": "...", "message": "..." } }` 形式で統一）
- バリデーションは design の方針に従い、共有関数に集約できる場合はまとめる

## 注意事項

- 仕様にない機能を勝手に追加しない（必要なら `/spec` に戻る）
- 既存コードの大幅リファクタは行わない（最小差分で動かす）
- 生成失敗時はEditで修正、Writeで全体書き換えしない
- lint、型チェック、テスト、buildが通るまで完了と報告しない。実際の操作はブラウザでも確認する
- テストコマンドやlintコマンドは対象プロジェクトの設定から判断する
