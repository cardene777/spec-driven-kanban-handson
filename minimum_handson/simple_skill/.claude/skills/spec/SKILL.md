# /spec

「こういう機能が欲しい」という自然言語の要望を、AIと人間の両方が誤解しない構造化仕様に変換するスキル。
仕様駆動開発の出発点となるドキュメントを作る。

第2章のミニマムハンズオンでは、プロンプトだけで作ったものと同じ最小構成のカンバンアプリ全体を、仕様を残しながらもう一度作る。
以下の4つを1回の `/spec` で仕様化する。
出力は1ファイルでも複数ファイルでもよいが、カンバンアプリ全体が実装できるようにspec/配下へまとめて書き出す。

1. ボード一覧とボード作成
2. ボード詳細とリスト作成
3. カード追加と表示
4. カードタイトル編集

ボード削除、リスト削除、カード削除、ボード編集、リスト編集は第2章では仕様化しない。
ユーザーが明示的に求めた場合でも、第2章の範囲を超えることを伝え、必要ならメインハンズオン以降の拡張として扱う。

## トリガー条件

以下のいずれかに該当する場合に呼び出す。

- 「ボードを作る機能の仕様を書いて」、「カード追加の仕様を書いて」
- 新機能を追加する前
- 既存機能の仕様を整理したいとき

## 入力

- `constitution.md`（プロジェクトルートから自動読み込み）
- 機能の自然言語要望（例「カードを追加できるようにしたい」）
- 関連する既存仕様（`spec/*.md` から関連を判断して読み込み）

## 出力

第2章ではspec/配下にカンバンアプリ全体の仕様を生成する。
分割する場合は、ボード、リスト、カード、カード編集、共通ルールなど、実装時にまとめて読める単位にする。
構成は以下のとおり。

```markdown
# {機能名}の仕様

## 概要

{1〜2文で機能を要約する}

## 機能要件

### FR-001 {要件のタイトル}

- 入力 {何を受け取るか}
- 条件 {どんなときに成立するか}
- 出力 {何を返すか}
- 振る舞い {1〜2文で動作を説明}

### FR-002 {次の要件}

（同じ形式で続ける）

## 異常系

| ID | 条件 | HTTPステータス | レスポンス |
|---|---|---|---|
| E-001 | {異常条件1} | {ステータス} | {メッセージ} |
| E-002 | {異常条件2} | {ステータス} | {メッセージ} |

## 境界条件

- {境界条件1（例 タイトル0文字、100文字、101文字）}
- {境界条件2}

## バリデーション

| フィールド | 必須 | 制約 |
|---|---|---|
| {フィールド名} | はい/いいえ | {型、長さ、形式} |

## 並び順

- 親内に0件なら `order` は0、以後は既存の最大値+1
- 同じ親内で `order` を重複させない

## 参考

- constitution.md {該当する原則}
- {関連する既存spec}
```

## 作業手順

1. Constitution確認
   `constitution.md` を読み込み、プロジェクトの前提を把握する。
2. 要望の聞き取り
   ユーザーから機能の要望を聞き取る。
3. 既存spec確認
   関連する既存specがあればspec/ディレクトリをGlobで探して読み込む。
4. 要望の具体化
   要望を以下の観点で具体化する。
   - 正常系 何が起きれば成功か
   - 異常系 失敗パターンとHTTPステータス
   - 境界条件 上限・下限・空・最大値
   - バリデーション フィールドごとの制約
   - 並び順 親内での初期値、採番、重複禁止
   - エラー形式 `{ "error": { "code": "...", "message": "..." } }`
   - 判定順序 対象リソースが無い場合は404を先に返し、対象がある場合だけ入力を検証して400を返す
5. spec生成
   上記テンプレートに従ってspec/配下に仕様を生成する。
6. 曖昧箇所の確認
   曖昧な箇所をClaude Codeが見つけたら、AskUserQuestionで確認する。
7. ファイル書き出し
   ユーザー承認後にファイルを書き出す。

## 注意事項

- 「適切に」、「できるだけ」など曖昧な表現は禁止
- 数値は具体値で書く（例「速い」ではなく「200ms以内」）
- 異常系は必ず1つ以上書く（書くことがなければ書かない理由を仕様に明記）
- 第2章では1回の `/spec` でカンバンアプリ全体を扱う。1ファイルでも複数ファイルでもよいが、ボード一覧だけなど完成物の一部だけで止めない
- 複数ファイルに分ける場合は、最後に「生成した全仕様を `/design` で整理し、`/implement` でまとめて実装する」前提が分かるようにする
- 第2章では軽量な `/design` を前提にする。データモデル・API・UIの最低限の判断はspec内に残し、実装前にdesignで再整理する
- 仕様はプロンプトだけで作ったものと同じ成果物を作るためのものであり、第2章の範囲外の機能を勝手に追加しない
- 第2章のBoard、List、Cardのtitleは、前後の半角・全角空白、タブ、改行を除去してから文字数を検証し、トリム後の値を保存する
