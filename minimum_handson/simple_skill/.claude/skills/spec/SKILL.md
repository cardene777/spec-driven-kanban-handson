# /spec

「こういう機能が欲しい」という自然言語の要望を、AIと人間の両方が誤解しない構造化仕様に変換するスキル。
仕様駆動開発の出発点となるドキュメントを作る。

渡された要望の範囲を仕様化する。要望に含まれない機能を勝手に追加しない。
ユーザーが明示的に範囲外を求めた場合は、その旨を伝えてから、必要なら別の仕様として扱う。

## トリガー条件

以下のいずれかに該当する場合に呼び出す。

- 「{機能名}の仕様を書いて」、「この要望を仕様にして」
- 新機能を追加する前
- 既存機能の仕様を整理したいとき

## 入力

- `constitution.md`（プロジェクトルートから自動読み込み）
- 機能の自然言語要望
- 関連する既存仕様（`spec/*.md` から関連を判断して読み込み）

## 出力

`spec/` 配下に仕様を生成する。
1つの要望が複数機能にまたがる場合は、実装時にまとめて読める単位（機能ごと、共通ルールごと）に分割してよい。
分割するかどうか、ファイル名は、ユーザーの指定があればそれに従い、なければ提案して確認する。
構成は以下のとおり。

```markdown
# {機能名}の仕様

## 概要

{1〜2文で機能を要約する}

## 機能要件

### FR-001 {要件のタイトル}

- 入力 {何を受け取るか}
- 条件 {どんなときに成立するか}
- 出力 {何を返すか}
- 振る舞い {1〜2文で動作を説明}

### FR-002 {次の要件}

（同じ形式で続ける）

## 異常系

| ID | 条件 | HTTPステータス | レスポンス |
|---|---|---|---|
| E-001 | {異常条件1} | {ステータス} | {メッセージ} |
| E-002 | {異常条件2} | {ステータス} | {メッセージ} |

## 境界条件

- {境界条件1（例 入力の下限・上限・空）}
- {境界条件2}

## バリデーション

| フィールド | 必須 | 制約 |
|---|---|---|
| {フィールド名} | はい/いいえ | {型、長さ、形式} |

## 並び順

（並び順を持つデータがある場合のみ）
- 親内に0件なら `order` は0、以後は既存の最大値+1
- 同じ親内で `order` を重複させない

## 参考

- constitution.md {該当する原則}
- {関連する既存spec}
```

## 作業手順

1. Constitution確認
   `constitution.md` を読み込み、プロジェクトの前提を把握する。
2. 要望の聞き取り
   ユーザーから機能の要望を聞き取る。
3. 既存spec確認
   関連する既存specがあればspec/ディレクトリをGlobで探して読み込む。
4. 要望の具体化
   要望を以下の観点で具体化する。
   - 正常系 何が起きれば成功か
   - 異常系 失敗パターンとHTTPステータス
   - 境界条件 上限・下限・空・最大値
   - バリデーション フィールドごとの制約
   - 並び順 （該当する場合）親内での初期値、採番、重複禁止
   - エラー形式 `{ "error": { "code": "...", "message": "..." } }`
   - 判定順序 対象リソースが無い場合は404を先に返し、対象がある場合だけ入力を検証して400を返す
5. spec生成
   上記テンプレートに従ってspec/配下に仕様を生成する。
6. 曖昧箇所の確認
   曖昧な箇所を見つけたら、AskUserQuestionで確認する。
7. ファイル書き出し
   ユーザー承認後にファイルを書き出す。

## 注意事項

- 「適切に」、「できるだけ」など曖昧な表現は禁止
- 数値は具体値で書く（例「速い」ではなく「200ms以内」）
- 異常系は必ず1つ以上書く（書くことがなければ書かない理由を仕様に明記）
- 渡された要望の全体を仕様化する。要望の一部だけで止めない
- 複数ファイルに分ける場合は、最後に「生成した全仕様を `/design` で整理し、`/implement` でまとめて実装する」前提が分かるようにする
- ドメイン固有のエンティティ名や機能名をスキル内で固定しない。要望から読み取る
- 入力文字列のトリム・文字数検証などの共通方針は `constitution.md` に従う
