# /constitution

プロジェクト立ち上げ時に1度だけ呼び出して `constitution.md` を生成するスキル。
ここで決めた技術スタックと原則が、その後の仕様化・設計・実装すべての前提になる。

## トリガー条件

以下のいずれかに該当する場合に呼び出す。

- 「プロジェクトの方針を決めて」、「技術スタックを決めて」、「constitutionを作って」
- 新しいリポジトリで最初に1度だけ実行する場合

## 入力

ユーザーから以下を聞き出す。聞かれなかった項目はデフォルトを採用する。

- プロジェクト名と1行説明
- 技術スタック（デフォルトNext.js + TypeScript + SQLite + Prisma + Tailwind CSS）
- 想定する規模（個人開発 / チーム開発）
- セキュリティ要件（認証要否、機密データの有無）
- コーディング規約（命名規則、ファイル構成、テスト方針）

## 出力

`./constitution.md` を生成する。
構成は以下のとおり。

```markdown
# {プロジェクト名} Constitution

## プロジェクト概要

{1行説明}

## 技術スタック

- フロントエンド {フレームワーク+UI}
- バックエンド {APIフレームワーク}
- データベース {DB+ORM}
- スタイル {CSSフレームワーク}
- テスト {テストランナー}
- パッケージマネージャ {npm/pnpm/yarn}

## コーディング規約

### 命名規則

- 変数・関数camelCase
- 型・コンポーネントPascalCase
- ファイル名kebab-caseまたはフレームワーク慣習

### ファイル構成

- `app/` Next.js App Routerのルーティング
- `lib/` 共有ロジック
- `prisma/` データベーススキーマ
- `tests/` テストコード

### コメント方針

- 「何を」ではなく「なぜ」を書く
- 自明なコメントは書かない

## 基本原則

### シンプルさ優先

- 動く最小実装を先に、抽象化は必要になってから
- 早すぎる最適化は避ける

### 仕様駆動

- 仕様を書いてから実装する
- 仕様変更は実装変更より先に行う

### 異常系の網羅

- 正常系だけでなく異常系・境界条件も仕様に含める
- HTTPステータスとエラーメッセージを統一する

## セキュリティ要件

{ユーザー回答に応じて生成}

## 成功基準

このConstitutionを満たすことが、本プロジェクトの最低品質ラインとする。
変更が必要な場合は本ファイルを更新してから実装に反映する。
```

## 作業手順

1. 作業ディレクトリ確認
   `./constitution.md` を作成する作業ディレクトリを確認する。
2. 項目の聞き取り
   ユーザーに上記項目を聞き出す。聞かなかった項目はデフォルトを採用する。
3. Constitution生成
   上記テンプレートに従って `constitution.md` を生成する。
4. 承認確認
   生成内容をユーザーに見せ、承認を得る。
5. ファイル書き出し
   承認後、`./constitution.md` に書き出す。

## 注意事項

- このスキルは1プロジェクトで1度だけ呼び出す
- 変更が必要な場合は本スキルを再実行するのではなく `constitution.md` を直接編集する
- `/spec` `/design` `/implement` は本ファイルを先頭で必ず読み込む
