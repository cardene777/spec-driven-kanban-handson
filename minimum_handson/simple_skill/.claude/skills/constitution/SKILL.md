# /constitution

プロジェクト立ち上げ時に1度だけ呼び出して `constitution.md` を生成するスキル。
ここで決めた技術スタックと原則が、その後の仕様化・実装すべての前提になる。

## トリガー条件

以下のいずれかに該当する場合に呼び出す。

- 「プロジェクトの方針を決めて」、「技術スタックを決めて」、「constitutionを作って」
- 新しいリポジトリで最初に1度だけ実行する場合

## 入力

ユーザーから以下を聞き出す。指定がなかった項目は、下記の「デフォルトの決め方」に従って提案し、確認を取る。

- プロジェクト名と1行説明
- 技術スタック（フロントエンド、バックエンド、DB・ORM、スタイル、テストランナー、パッケージマネージャ）
- 想定する規模（個人開発 / チーム開発）
- セキュリティ要件（認証要否、機密データの有無）
- コーディング規約（命名規則、ファイル構成、テスト方針）

### デフォルトの決め方

- ユーザーが技術スタックを指定した場合は、それを尊重する。
- 指定がない場合は、リポジトリの既存ファイル（`package.json`、設定ファイル、既存コード）から使用中の技術を推定して提案する。
- 既存ファイルもない場合は、汎用的で標準的な構成を1つ提案し、ユーザーに確認する。スキル側で特定のフレームワークやテストランナーを固定しない。

## 出力

`constitution.md` をプロジェクトルートに生成する。
構成は以下のとおり。

```markdown
# {プロジェクト名} Constitution

## プロジェクト概要

{1行説明}

## 技術スタック

- フロントエンド {フレームワーク+UI}
- バックエンド {APIフレームワーク}
- データベース {DB+ORM}
- スタイル {CSSフレームワーク}
- テスト {テストランナー}
- パッケージマネージャ {npm/pnpm/yarn}

## コーディング規約

### 命名規則

- 変数・関数camelCase
- 型・コンポーネントPascalCase
- ファイル名kebab-caseまたはフレームワーク慣習

### ファイル構成

- {ルーティング層のディレクトリ}
- {共有ロジックのディレクトリ}
- {データベーススキーマのディレクトリ}
- {テストコードのディレクトリ}

### コメント方針

- 「何を」ではなく「なぜ」を書く
- 自明なコメントは書かない

## 基本原則

### シンプルさ優先

- 動く最小実装を先に、抽象化は必要になってから
- 早すぎる最適化は避ける

### 仕様駆動

- 仕様を書いてから実装する
- 仕様変更は実装変更より先に行う

### 入力エラーと境界値

- 空文字、文字数上限、存在しないIDへのアクセスを仕様に含める
- HTTPステータスと `{ "error": { "code": "...", "message": "..." } }` のエラー形式を統一する

## セキュリティ要件

{ユーザー回答に応じて生成}

## 成功基準

このConstitutionを満たすことが、本プロジェクトの最低品質ラインとする。
変更が必要な場合は本ファイルを更新してから実装に反映する。

## 検証コマンド

- lint {対象プロジェクトの lint コマンド}
- typecheck {型チェックコマンド。型付き言語の場合}
- test {テスト実行コマンド}
- build {ビルドコマンド}
```

## 作業手順

1. プロジェクトルート確認
   プロジェクトルートを確認する。既存の `package.json` や設定ファイルがあれば読み、使用中の技術を把握する。
2. 項目の聞き取り
   ユーザーに上記項目を聞き出す。指定がない項目は「デフォルトの決め方」に従って提案し、確認を取る。
3. Constitution生成
   上記テンプレートに従って `constitution.md` を生成する。
4. 承認確認
   生成内容をユーザーに見せ、承認を得る。
5. ファイル書き出し
   承認後、`constitution.md` をプロジェクトルートに書き出す。

## 注意事項

- このスキルは1プロジェクトで1度だけ呼び出す
- 変更が必要な場合は本スキルを再実行するのではなく `constitution.md` を直接編集する
- `/spec` `/design` `/implement` は本ファイルを先頭で必ず読み込む
- 特定のフレームワーク、テストランナー、ORM をスキル内で固定しない。技術は入力とリポジトリの実態から決める
- 検証コマンドは、技術スタックが決まったあとに、そのスタックの標準的なコマンドを記録する
