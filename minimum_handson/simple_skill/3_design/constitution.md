# Simple Kanban Constitution

## プロジェクト概要

タスクをカードで管理する最小構成のカンバンアプリ。

## 技術スタック

- フロントエンド Next.js (App Router) + TypeScript
- バックエンド Next.js Route Handlers (API Routes)
- データベース SQLite + Prisma
- スタイル Tailwind CSS
- テスト Vitest
- パッケージマネージャ npm

## コーディング規約

### 命名規則

- 変数・関数 camelCase
- 型・コンポーネント PascalCase
- ファイル名 kebab-case (Next.js の慣習に従い `page.tsx` / `route.ts` など特殊 file は例外)

### ファイル構成

- `app/` Next.js App Router のルーティング・画面・API
- `lib/` DB クライアント・共有ロジック
- `prisma/` `schema.prisma` とマイグレーション
- `tests/` Vitest のテストコード

### コメント方針

- 「何を」ではなく「なぜ」を書く
- 自明なコメントは書かない
- 型・変数名で意図を伝えられるならコメントは不要

## 基本原則

### シンプルさ優先

- 動く最小実装を先に、抽象化は必要になってから追加する
- 早すぎる最適化は避ける
- 個人開発なので依存関係は最小限に絞る

### 仕様駆動

- 仕様 (`spec.md`) を書いてから実装する
- 仕様変更は実装変更より先に行う
- `/spec` → `/design` → `/implement` の順で進める

### 異常系の網羅

- 正常系だけでなく異常系・境界条件も仕様に含める
- HTTP ステータスとエラーメッセージを統一する (400 / 404 / 500 の 3 種を基本とする)
- 入力バリデーションは API 層で行う

## セキュリティ要件

- 個人開発想定、認証は実装しない
- 機密データは扱わない (タスクのタイトル・説明など公開されても問題ない情報のみ)
- SQLite file はローカル配置、外部公開しない
- 入力値は Prisma 経由で扱い、生 SQL は書かない (SQL インジェクション対策)

## 成功基準

この Constitution を満たすことが、本プロジェクトの最低品質ラインとする。
変更が必要な場合は本ファイルを更新してから実装に反映する。
